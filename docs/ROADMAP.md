# 원작 모드 남은 작업 구현 계획

작성: 2026-10-01, `main` `bc13042`(v0.2.1) 기준. 아래 `파일:줄`은 이 커밋 기준이라 작업할 때는 함수 이름으로 다시 찾는다.
**무엇을** 할지는 [BACKLOG.md](../BACKLOG.md)와 이슈 #79(Hardening candidates: v0.2.1)가 정한다. 이 문서는 **어떤 순서로·어떻게**
할지를 적는다. 단계 하나가 끝나면 이 문서의 체크박스와 BACKLOG를 함께 갱신한다.

## 0. 진행 방식

- **단계(M)마다 PR 하나.** 리뷰 에이전트와 Codex 리뷰를 받고, 리뷰 본문과 인라인 코멘트를 모두 처리한 다음 머지한다.
- **매 단계의 검증**
  - `cargo test --workspace`를 돌린다.
  - 원작이 있을 때만 도는 골든 테스트 4종을 돌린다. 이때 `EIKETSU_ORIGINAL_DIR=<설치 폴더>`를 설정한다.
  - `hero-tools validate`를 돌린다.
  - 변환 결과가 바뀌는 단계는 M1-2의 팩 diff 요약을 PR 본문에 붙인다.
- **기능이 머지되면 문서 세 곳을 갱신한다**: README 진행 상황, `docs/reverse-engineering/STATUS.md` §2–4, `docs/ORIGINAL_DATA.md` §7–8.
- **이슈 #79를 소진하는 단계(M1)에서는 새 하드닝 이슈를 만들지 않는다.** 그 단계에서 드러난 개선점은 #79의 남은 체크리스트나
  BACKLOG에만 적는다.
- **데이터 형식이 바뀌면 DECISIONS에 기록한다.** 엔진이 읽는 형식(`battledef`·`campaign`·세이브)을 바꾸는 단계(M2·M4)는
  DECISIONS에 결정을 남기고 MODDING.md를 갱신한다.
- **릴리스는 묶음 단위로 한다**: M1–M4 뒤에 v0.3.0, 원작에 없는 선택 기능(X 단계, D25) 묶음이 v0.4.0, M5 이후가 그다음 마이너다. 릴리스 때는 하드닝 후보를 이슈로 등록한다.

## M0. 원작 동적 관찰 환경

### 왜 필요한가

남은 항목 중 일부는 정적 분석만으로 끝내기 어렵다.

- 도착 칸 (M3)
- 팔레트 슬롯 (M5-1)
- 전투 중 곡 (M5-4)

원작을 에뮬레이터로 돌려 **화면·메모리·OPL 출력을 관찰**하면 이것들을 사실로 확정할 수 있다. 원작과 같은 지점의 상태를
준비해 두면 사람이 하는 난이도 비교(H)도 빨라진다.

### 공개된 원칙과의 관계 (D22로 해결)

`docs/reverse-engineering/README.md`의 원칙 3과 `ORIGINAL_DATA.md`에는 이 PR 전까지 **"원작 실행 파일은 한 번도 실행하지 않았고,
DOSBox 등 에뮬레이터로 돌려 본 적도 없다"** 고 적혀 있었다. `METHOD.md` §5에는 "에뮬레이터 비교가 필요하면 별도 결정"이라고
되어 있었다. 그래서 소유자의 결정(D22)을 먼저 받고, 원칙 문구를 "v0.2.1까지는"의 기록과 이후의 관찰 규칙으로 고쳤다.

### D22 (2026-10-01 승인, DECISIONS에 기록)

원작은 공식 DOSBox-X에서 관찰용으로만 실행한다. 규칙은 다음과 같다.

- 설치 폴더의 복사본(`res/dosbox/GAME`)에서만 실행한다.
- 복제 방지는 소유자가 설명서로 답하고, 우회하지 않는다.
- 패키지의 `DOSBox.exe`·`CRACK.COM`은 실행하지 않는다.
- 캡처·덤프는 로컬에만 두고, 문서에는 사실만 **[관찰]** 로 적는다.

원칙 문구(역공학 README 원칙 3, ORIGINAL_DATA)도 함께 고쳤다. 운영 방법은 METHOD 2.8절에 있다.

### 준비 작업

1. DOSBox-X를 준비한다(2026-10-01 승인, 완료).
   - winget 설치기는 관리자 권한을 요구해 쓰지 않았다.
   - 대신 같은 공식 릴리스의 포터블 zip을 `res/dosbox/app`에 풀었다.
   - 원작은 시작할 때 **복제 방지 코드**(설명서 대조)를 묻는다. 소유자가 입력하고, 그 직후의 에뮬레이터 상태를 저장해 이후에 다시 쓴다.
2. `res/dosbox/`를 만든다. 들어갈 것:
   - `GAME` 복사본
   - `dosbox-x.conf`
     - 원작 패키지 `dosbox.conf`와 같은 값을 쓴다.
       - 기계: `machine=svga_s3`, `memsize=16`, `core=normal`, `cycles=fixed 8000`. 원작의 속도에 맞춘 값으로 보인다.
       - 소리: `sbtype=sb16`, `sbbase=220`, `irq=7`, `dma=1`, `oplmode=auto`, `oplrate=44100`.
     - `[autoexec]`에는 `mount c GAME`, `c:`, `HERO`를 넣는다.
     - `[capture] captures=` 경로를 지정한다.
3. **가능성 시험(spike)**: 아래가 되는지 하나씩 확인하고, 결과를 METHOD 2.8절("에뮬레이터 관찰")에 적는다.
   - [x] 원작이 뜨는가: 뜬다. 첫 화면이 복제 방지 코드 입력이다. 제목 화면과 소리는 코드를 입력한 뒤 확인한다.
   - [x] 키 입력 자동화가 되는가
     - DOSBox-X `AUTOTYPE`는 된다.
     - 창 메시지(PostMessage)는 안 된다.
     - 대화형 입력은 데스크톱 자동화로 한다.
   - [x] 화면 캡처가 되는가: `PrintWindow`로 된다. 잠긴 화면에서도 되는지는 아직 확인하지 않았다.
   - **BLOCKED (2026-10-01)**: 소유자에게 설명서·코드표가 없어 복제 방지 코드에 답할 수 없다. 우회하지 않으므로 아래 항목은
     확인하지 못했다. 환경은 남겨 두고, 설명서가 생기면 여기서 이어 간다(METHOD 2.8).
   - [ ] 상태 저장과 불러오기가 되는가. 전투 시작 직전의 상태를 저장해 두는 것이 핵심이다.
   - [ ] 디버거가 되는가: 브레이크포인트, 메모리 감시, `MEMDUMPBIN`으로 DS 영역 덤프
   - [ ] OPL 출력 기록(`.dro` 또는 원시 OPL 로그)이 되는가
   - [ ] 기존 세이브 `MSAVE1–4`(2000년)를 불러오면 어느 장·어느 위치인가. 중간 장으로 바로 갈 수 있는지 본다.
4. **실패 처리**: 같은 방식이 3번 실패하면 방식을 바꾼다. 예를 들어 자동 입력이 안 되면 사람이 상태 저장 지점까지 데려다 주게 한다.
   그래도 안 되면 그 항목을 BLOCKED로 기록한다.

**완료 기준**: D22가 DECISIONS에 있고(완료), 원칙 문구가 고쳐져 있고(완료), 위 체크리스트의 결과가 METHOD 2.8절에 적혀 있다(완료,
본편 관찰은 BLOCKED).

**관찰이 막힌 동안의 원칙**: 아래 M3·M5의 "관찰"과 "DOSBox" 항목은 설명서가 생기기 전까지 건너뛰고, 같은 항목의 정적 분석
경로로 확정한다. 정적 분석으로도 확정하지 못하면 지금처럼 [추론]으로 두고 BACKLOG에 남긴다. 관찰을 이유로 다른 단계를 막지 않는다.

## M2. 루트·조건에 따른 출진

**문제**

- 장 전투는 `flags: &[]`로 변환된다(`pack.rs:2684-2691`). 그래서 `if_flags`로 갈리는 명단은 "모든 플래그가 꺼진" 쪽으로 고정된다.
  예: 1장 계교는 거록 루트의 명단(플래그 133)이 아니라 청하 루트의 명단으로 고정된다.
- 출진 설정(`battles.rs:591-608`)은 `if_flags`를 보지 않는다. 승리 조건 무장(`defeat_to_win`)이 적 명단에 있는 마지막 설정을 고르고,
  없으면 승리 조건 무장이 없는 마지막 설정을 고른다.
  예: 4장 진창·장안은 방통 또는 조운이 "퇴각하면 패배"인데, 한쪽으로 고정된다.
- 사수관의 조건부 손님(공손찬·도겸, `requires_flag` 0·1)은 빠진다(`battles.rs:1938-1942`, `pack.rs:2823`).

**설계 (D23로 기록할 결정)**: 두 가지 수단을 함께 쓴다.

1. **조건부 유닛**: `UnitSpawn`에 `when`/`unless: Vec<FlagCond>`를 더한다. `EventDef`와 같은 형식이다(`battledef.rs:330-350`).
   - 전투를 준비할 때(`battle/setup.rs` `build`) 캠페인 플래그로 평가해서, 조건이 맞지 않는 유닛은 아예 만들지 않는다.
   - 쓰는 곳: 명단의 일부만 다른 루트(계교), 사수관 손님(플레이어 쪽 조건부 출진 칸).
2. **루트별 전투**: 출진 설정이 다를 때만 쓴다. 출진 설정이란 승리 조건 무장, "퇴각하면 패배" 무장, 플레이어 출진 칸을 말한다.
   - 변환기가 루트 조합마다 전투 `<id>` / `<id>~<루트>`를 만든다.
   - 캠페인은 기존 `Node::Branch`(`campaign.rs:46`)로 캠프와 전투를 고른다.

**대안**: 모든 차이를 루트별 전투로 처리할 수 있다. 엔진 형식은 바뀌지 않지만 사수관 손님 둘만으로 4가지 조합이 생기고
캠프·세이브 노드가 늘어나서 택하지 않는다. 반대로 모든 차이를 조건부 유닛으로 처리하려면 승리·패배 조건까지 조건부로
만들어야 해서 형식 변경이 커진다.

### 가이드

1. **엔진 (hero-core)**
   - `UnitSpawn`에 `#[serde(default)] when`, `unless`를 추가한다.
   - `setup.rs`에서 유닛을 만드는 반복(`spawn_unit` 호출부)에서 `FlagCond`를 평가한다.
     - 이벤트 쪽 평가는 `BattleState`의 메서드다(`battle/mod.rs`의 `conditions_hold`/`flags_allow`, 530–541 부근).
       그래서 플래그 맵을 받는 자유 함수로 분리해 두 곳이 같이 쓴다.
     - `build`의 `spawned` 클로저(`setup.rs:40-44`)도 같은 평가를 거친다. 그래야 조건이 맞지 않아 만들지 않는 Player 유닛의
       무장이 출진 칸에서 빠지지 않는다.
   - 원작 `if_flags`의 `all_set`과 `all_clear`는 **모두 `when`에 넣는다**. `all_clear`는 `== 0` 비교로 표현한다.
     `unless`는 "모두 성립하면 막음"이라, `all_clear`가 둘 이상일 때 `unless`로 옮기면 뜻이 달라진다.
   - 플레이어 쪽 조건부 유닛은 "그 전투만 함께하는 손님"이다. 군에 넣지 않는다.
   - 검증(`pack/validate.rs`)
     - 조건부 유닛의 무장이 `deploy.required`에 있으면 오류로 한다.
     - 지금 검증은 같은 무장이 두 번 나오거나(1009–1013 부근) 같은 칸에 유닛이 둘이면(1091 부근) 오류를 낸다.
       루트별 명단은 이 두 경우에 걸리므로, **조건이 서로 배타적인 유닛끼리는** 이 오류를 면제한다.
       배타적인지는 같은 플래그를 한쪽은 켜짐, 다른 쪽은 꺼짐으로 요구하는지로 판정한다. 배타적이 아니면 지금처럼 오류다.
   - 세이브: 전투 도중 세이브에는 이미 만들어진 유닛이 들어가므로 영향이 없다. 확인 테스트를 하나 둔다.
2. **변환기 (hero-import)**
   - `find_battle_leg`(`battles.rs:506-673`)가 명단을 고를 때 **모든 루트의 명단을 모은다**. 지금은 `other_route_rosters` 개수만 센다.
     각 유닛에 `if_flags`를 `FlagCond`로 붙이고, 원작 플래그 `n`은 `orig_f<n>`으로 바꾼다.
     두 루트의 명단에 같은 유닛(같은 칸·같은 인물)이 있으면 조건 없이 하나로 합친다.
   - 출진 설정은 `if_flags`별로 모은다. 서로 다른 설정이 2개 이상이면 루트별 전투로 나눈다:
     - `chapters.rs`의 캠프·전투 노드 앞에 `Branch`를 넣는다.
     - `battle_leg`처럼 전투 id 접미사를 정한다.
   - 사수관: `requires_flag`가 있는 플레이어 칸은 조건부 Player 유닛(손님)이 된다. 플래그 0·1은 `orig_f0`·`orig_f1`이다.
     이 플래그를 켜는 캠프 대화가 변환되어 있는지 먼저 확인한다(`flow0.md`). 없으면 그 대화도 옮긴다.
   - "다른 루트 명단은 쓰지 않음" notes는 지운다. 대신 "루트 조건부 유닛 N개", "루트별 전투 N개"를 기록한다.
3. **테스트**
   - 합성: `if_flags`가 둘인 블록이 조건부 유닛 두 묶음이 되는지, 설정이 다를 때 전투가 둘로 나뉘는지 본다.
   - 골든:
     - 계교의 적 명단이 루트별로 원작과 같은지
     - 진창·장안이 루트별로 다른 "퇴각하면 패배" 무장을 갖는지
     - 사수관에 손님 두 칸이 조건부로 있는지
4. **문서**: MODDING.md(유닛 `when`), DECISIONS D23, BACKLOG의 "남은 루트와 조건" (4)와 "서장·1장 실물 확인" (1)·(2)를 닫는다.

**DOSBox 활용(선택)**: 같은 전투를 두 루트로 진행한 상태 저장을 만들어, 원작의 출진 화면이 우리 변환과 같은지 캡처로 비교한다.

**결과 (2026-10-01, PR #85)**: 설계를 바꿨다(DECISIONS D23).
- **루트별 전투 하나로 처리**: 조건부 유닛(엔진 형식)은 넣지 않았다. 명단만 다른 경우(계교)도 출진 설정이 다른 경우(진창·장안)와
  똑같이 루트별 전투로 처리하면 엔진과 공개 형식이 바뀌지 않는다.
- **`find_battle_leg`**: 출진 설정에도 `if_flags`를 적용한다. 손님 칸은 플래그가 켜져 있을 때만 넣는다. 전투가 보는 플래그를
  `route_flags`로 알려 준다.
- **어느 루트의 전투인지 가리는 규칙 두 가지**
  - 그 루트가 전투에 맞는 설정이 있는 마지막 블록의 설정을 모두 건너뛰면, 그 루트의 전투가 아니다.
  - 맵을 읽은 뒤의 설정은 다음 전투의 것이다.
- **변환기**: `route_variants`가 플래그 조합마다 다시 읽어 서로 다른 것만 변형으로 만든다. 이야기가 정해 두는 플래그는 나누지 않는다.
- **캠페인**: `chapters::BattleChoice`와 캠프 앞 `<id>_which` 분기로 변형을 고른다.
- **실물에서 생긴 변형**: 계교(133), 진창·장안(38), `c4_s2_b2`(218). 사수관·호로관은 손님이 자기 칸의 우군으로 서고 변형은 없다.
- **함께 찾아 고친 결함 #84**: 합류하지 않는 동맹 무장이 출진 필수가 되던 문제. 서장 2개, 1장 7개 전투에 해당한다.
- 허창 2(`c4_s1_b7`)의 개막(첫 감시 단계 앞의 `run` 단계)을 전투 시작 이벤트로 옮겨, 플래그 218이 켜지고 `c4_s2_b2_f218`에 닿게 됨
  (리뷰에서 찾음: 전에는 개막이 빠져 218이 켜지지 않았다). 같은 방식의 개막이 있는 `c3_s2_b10`도 개막 대사가 나온다.
- 가이드 4(MODDING의 유닛 `when`)는 해당 없음.

## M3. 전투 중 도착하는 아군

**현재**

- `join_battle`(`battles.rs:1696-1723`)은 도착 그룹이 있으면 `Spawn`을 만든다.
- 그러나 도착하는 무장이 "군의 무장"이면(`Some(None)`) 대사만 옮긴다.
- 도착 무장은 모두 `Side::Ally`가 되고 출진이 금지된다(`pack.rs:2929-2946`).
- 그래서 허창 1(`c4_s1_b6`)의 별동대는 캠프 전에 합류해 처음부터 출진할 수 있고, 12턴에는 대사만 나온다.
- `set_allegiance`는 "옮기지 않음" 기록만 남긴다(`battles.rs:1830-1836`).

**선행 작업: 도착 칸 확정.** 원작 `join_battle`은 무장 번호만 준다. 명단에도 출진 칸에도 이 무장의 자리가 없다.

- 정적 분석: `join_battle` 처리 루틴(스크립트 op 디스패치에서 찾음)이 칸을 고르는 방식을 따라간다.
  "적 근처 빈 칸" 같은 규칙인지, 표에서 읽는지 확인한다.
- **DOSBox(M0)**: 허창 1을 12턴 직전까지 진행한 상태를 저장한 뒤, 도착 순간의 화면과 유닛 표 메모리를 덤프한다.
  두세 번 반복해서 칸이 고정인지 규칙인지 본다. 이것이 가장 빠르다.

**가이드 (엔진은 대부분 이미 됨)**

- `setup.rs:224-232`의 `army_officer`: Player 쪽 유닛의 무장이 군에 있으면 그 무장의 상태를 쓴다.
  `group`이 있는 유닛은 `Hidden`으로 시작한다(`setup.rs:267-271`). 그래서 **Player 쪽 + group 유닛**이면 엔진 변경 없이 된다.
- 변환기 처리:
  - 도착 무장이 그때 군에 있으면(`in_army`) 유닛을 `Side::Player` + `group = original_<record>`로 만든다.
  - 출진 금지는 새 코드가 필요 없다. `pack.rs:2929-2946`이 적이 아닌 무장 유닛을 이미 모두 `DeployDef.forbidden`에 넣는다.
  - 칸은 선행 작업의 결과로 정한다.
    - **고정 칸**이면(원작 표에서 온 값) 그 표를 읽는 코드의 서명으로 사용자 파일에서 읽는다. 관찰한 좌표를 상수로 넣지 않는다(D22·원칙 6).
    - **"기준 칸에서 가장 가까운 빈 칸"** 규칙이면 지금의 `spawn_group`(`flow.rs:456-478`)으로 된다.
    - **"그때 적 근처"처럼 동적인 규칙**이면 `spawn_group`에 기준을 고르는 방식을 더해야 하므로, 엔진 변경으로 따로 설계한다.
- 허창 2의 황충·엄안 도착과 `set_allegiance`:
  - `EventAction::SetSide { target, side }`를 추가한다. 이때 `unit_refs`(`battledef.rs:454-477`)와 `run_action`(`flow.rs:374-450`)에도 갈래를 더한다.
  - 소속이 바뀐 유닛의 AI와 턴 순서를 처리한다. 바뀐 페이즈부터 새 편으로 움직인다.
- 원작에서 도착 무장이 캠페인에 합류하는 시점(`@join`)이 전투 뒤인지 확인한다. 전투 앞의 `@join`이 문제의 원인이면 전투 뒤로 옮긴다.

## M5. 원작 동작 확정 (정적 분석 + 관찰)

각 항목은 독립적이다. 정적 분석으로 가설을 세우고, M0 환경에서 관찰로 확정한 뒤, 엔진과 변환기에 반영한다.

### M5-1. 16색 그림의 팔레트 슬롯

- **현재**: `MAP_PALETTE_SLOT = 1`(`extract.rs:1772`)과 `STATUS_PALETTE_SLOT = 0`(`pack.rs:993`)은 추론이다.
  PR #67에서 "그때의 장소 슬롯(DS 0x7A6C + 5의 하위 4비트)"까지 좁혔다(BACKLOG).
- **관찰**
  - 디버거로 `DS:0x7A6C+5`에 쓰기 감시를 걸고 캠프·전투에 들어간다. 쓰는 코드 위치와 값을 기록한다.
  - 장소 서너 곳에서 상태 창을 캡처해 후보 슬롯 색과 비교한다.
- **반영**: 슬롯이 장소마다 다르면 `convert_ui`(`pack.rs:1061-1153`)가 슬롯별로 그림을 여러 벌 만든다.
  장소 → 슬롯 대응은 원작 데이터(장소 레코드의 +8 바이트)에서 읽는다. 관찰한 대응을 표로 코드에 넣지 않는다.
  전투·캠프 정의가 쓸 벌을 고르게 하는데, 이때 형식이 늘어나는지 검토한다. 슬롯이 하나로 고정이면 상수만 고친다.

### M5-2. 편 전체 사기 절반 (스크립트 op `2D`, 이미지 0x2D5DD)

- [x] **완료 (2026-10-05)**: 정적 분석으로 확정했다. `a` 0 = 아군 측(우군 포함), 그 외 = 적군 측, `b` 0 = 사기(사기 함수를
  거침), 그 외 = 병력이고, 맵에 있는 유닛만 대상이다(FORMATS §13 op 표). 엔진 동작 `halve { side, stat }`(MODDING)로 옮겼고,
  원작 15번 가운데 14번을 옮긴다(2장 박망파 5, 3장 2+3, 4장 2+2). 이 과정에서 4장 마지막 두 전투가 전투로
  변환되지 않던 결함(이슈 #95)을 찾아 고쳤다. 남은 1번(2장 `c2_s1_b16`, 맵 21의 레코드 14)은 단계 사이에 도는 레코드의 플래그 138로 가드된
  부분에 있어 빠진다(단계 사이 레코드의 가드 부분은 변환하지 않음, 기존 노트). 관찰(메모리 확인)은 M0이 막혀 하지 않았다. 아래는 원래 계획이다.

- **정적 분석**: 추출된 시나리오(`res/extract/all`)에서 op `2D`를 쓰는 전투를 모두 찾는다(`scenario.rs:345`의 디코더). 인자 `a, b`의 뜻을 정한다.
- **반영**
  - `EventAction::MoraleHalve { side }`를 추가한다. `unit_refs`·`run_action`의 갈래도 더한다.
  - 원작 식에서는 사기 변화가 혼란을 일으킬 수 있으므로 `morale_set`(`strategy.rs:308-323`)을 거친다.
- **관찰**: 그 전투의 해당 시점에서 사기 수치를 메모리로 확인한다.

### M5-3. 적장 초기 장비가 원작에서 적용되는가

- **정적 분석**: 전투 유닛을 만드는 루틴이 `BAKDATA` 장비 칸을 읽는지 따라간다.
- **관찰**: 광천에서 적장(예: 장비가 있는 무장)의 상태 창 공격력과, 같은 무장의 장비 없는 계산값을 비교한다.
- **반영**: 적용되지 않는다면 적 유닛을 만드는 쪽에서 빈 장비를 준다.
  `original_equip`(`pack.rs:3706`)은 무장 정의(합류하는 아군 포함)도 쓰는 공용 함수라 고치지 않는다.

### M5-4. 곡 배정과 전투 중 곡

- **현재**: `MUSIC_KEYS`(`pack.rs:785-796`)는 문맥 추론이다. 장 전투는 `bgm:"battle"`/`bgm_enemy:"enemy"`로 고정되어 있다(`chapters.rs:1126-1127`).
- **관찰** (이 항목이 DOSBox로 가장 크게 얻는 부분이다)
  1. 장면별(제목, 캠프, 평시, 긴박, 슬픔, 패배, 아군 턴, 적 턴, 보스)로 OPL 출력을 기록한다.
  2. 우리 `music.rs`의 SBOPL2 이식이 내는 **레지스터 쓰기 순서**와 곡 번호별로 맞춰 본다.
     사람이 듣지 않아도 곡 번호를 기계적으로 확정할 수 있다.
     원작 기록에는 드라이버 초기화와 효과음 쓰기가 섞여 있다. 그래서 초기화 구간을 빼고, 음 높이·키온 쓰기만 골라
     **부분열 정렬**로 맞춘다. 앞부분을 그대로 비교하지 않는다.
  3. 같은 기록으로 인트로 길이와 루프 지점도 확인한다(M5-5).
- **반영**
  - `MUSIC_KEYS`를 고친다.
  - 전투마다 곡이 다르면 변환기가 전투별 `bgm`을 쓴다. 이때 `int 65h` 경로를 정적으로 따라가 규칙(전투 종류별 등)을 찾는다.
- **도구**: `hero-tools`에 `music trace <song>` 하위 명령을 둔다. 원작 곡을 우리 재생기로 돌린 OPL 레지스터 쓰기 목록을 출력한다.
  비교 스크립트는 스크래치에 둔다. trace 출력과 원작 OPL 기록은 픽스처로 커밋하지 않는다.

### M5-5. 음악 루프 시작점 (인트로 한 번 뒤 반복)

- **현재**
  - `audio.rs`는 파일째 반복만 한다(`play_bgm` 146–151, `play_sound`는 255–261).
  - 렌더러는 두 번째 바퀴의 루프 한 바퀴만 남긴다(`music.rs:236-310`).
- **가이드 (macroquad 0.4는 오프셋 루프가 없음)**
  - 변환기는 `bgm/<키>.wav`(루프)와 `bgm/<키>.intro.wav`(인트로, 있을 때만)를 쓴다. `ending`처럼 트랙마다 루프가 다른 곡은 지금처럼 한 파일로 둔다.
  - 엔진의 `play_bgm`은 인트로가 있으면 `looped: false`로 틀고, **인트로 길이(샘플 수 / rate)가 지나면** 루프 파일을 `looped: true`로 이어서 튼다.
    타이머는 `update`(214–289)에서 잰다.
  - 위험과 대응
    - 지금 곡 교체는 페이드 아웃 0.6 s 뒤 페이드 인 0.4 s다. 인트로 → 루프 전환은 이 페이드 경로를 거치지 않는 별도 전환으로 만든다.
    - 루프 파일은 인트로와 함께 미리 로드해서, 전환 시점에 준비가 끝나 있게 한다. 웹은 비동기로 로드한다.
    - 웹에서 탭이 백그라운드에 있으면 프레임 타이머가 멈출 수 있다. 그러면 인트로가 끝난 뒤 무음이 된다. 다시 앞으로 오면 곧바로 루프를 틀게 한다.
    - 전환 오차는 적어도 한 프레임이다. 인트로와 루프를 겹치면 두 번 재생되므로 겹치지 않는다.
  - 페이드나 곡 교체가 인트로 도중에 일어나면 타이머를 취소한다.
- **확인**
  - 단위 테스트: 인트로 → 루프 전환 타이머, 도중 교체 시 취소
  - 렌더 결과의 인트로 길이: battle 2.7 s, defeat 0.8 s, sad 0.4 s
  - 네이티브와 웹(헤드리스 Chrome)에서 전환 시점의 간격을 녹음해 **측정**하고, 그 값을 PR에 적는다

## M7. 순간 저장 편의 (BACKLOG "순간 저장")

1. **캠프 메뉴에 순간 저장·불러오기 항목을 추가한다.** `screens/camp/mod.rs`의 `Command`(54–65)는 전투가 있으면 10항목이다.
   640×400 캔버스에 12항목이 들어가는지 먼저 확인한다. 안 들어가면 "기록" 하위 메뉴로 묶는다.
2. **진행 중이던 연출의 남은 시간**: 지금처럼 끝난 상태로 불러온다. 문서에만 남기고 구현은 미룬다(D20 대안 A의 부담).
3. **여러 칸**: 요청이 있을 때만 한다. `SaveSlot::Quick`을 `Quick(u8)`로 바꾸고 직렬 형식 호환을 지킨다.
4. **팩 버전이 바뀌면 불러올 수 없는 문제**
   - `Cmd`의 안정적인 직렬 형식으로 장면 지문을 만들고, `check_resume`(`save.rs:159-187`)의 버전 비교를 지문 비교로 바꾼다.
   - 지문 형식이 게임 버전 사이에 변하지 않도록 고정 테스트를 둔다.
- **결과 (1·4)**: 캠프 메뉴에 '순간 저장'·'순간 불러오기'를 더했다(전투가 있으면 12항목; 가장 작은 480×270 캔버스에서 메뉴와 그
  아래 플레이 시간이 도움말 막대 위에서 끝나는 것을 테스트로 고정). 장면 기록은 저장할 때 `Scene::fingerprint`(명령·라벨의 JSON에
  FNV-1a 64, `v1:` 접두)를 함께 적고, 팩 버전이 달라도 지문이 같으면 이어 한다. 지문 값은 고정 테스트가 지킨다.
- **결과 (3, 요청으로 진행)**: `SaveSlot::Quick(u8)`, 칸 4개(`QUICK_SLOTS`). 1번 칸은 예전 한 칸의 키(`save_<팩>_quick`)를 그대로 써서
  옛 순간 저장이 1번 칸이 된다. 2~4번은 `quick2`~`quick4`. F5·F9는 설정의 `quick_slot` 칸을 쓰고, F6이나 설정 화면의 '순간 저장 칸'으로
  바꾼다. 불러오기 화면은 네 칸을 모두 보인다. 2는 위의 방침대로 하지 않았다.

## X. 원작에 없는 선택 기능 (D25)

원작 재현(M 단계)과 따로 간다. 규칙은 D25다. 기본값은 원작 그대로이고, 판의 규칙을 바꾸는 선택은 새 게임에서 정해
세이브에 두며(하나라도 켜면 세이브 버전 4와 목록 표시), 보기만 바꾸는 선택은 설정에 둔다. 새 게임 선택 묶음(X1·X3·X6)과
설정형 묶음(X2·X4·X5)이 PR 하나씩이다.

- [x] **X1. 난이도** (쉬움·기본·어려움 = 적 레벨 −2·0·+2)
  - `campaign::Difficulty`, `CampaignState::difficulty`; 전투를 세울 때 `battle/setup.rs` `defined_unit`이 적 레벨을 옮긴다.
  - 남은 것: 값(±2)은 사람이 해 본 뒤 조정한다(H). 기계 비교는 `hero-tools simulate --campaign --difficulty easy|hard`
    (`--extended-rules`도 있음, v0.4.1)로 한다.
- [x] **X3. 능력치 자유 조정** (새 게임에서 켠 판만)
  - `CampaignState::free_edit`, `set_ability`(1–100, 군의 무장만). 무장 정보 상세 화면에서 Z(또는 능력치 탭)로 편집하고
    ↑↓로 고르고 ←→(또는 그 줄의 왼쪽·오른쪽 탭)로 1씩 바꾼다. 길게 누르면(키·터치) 1초 뒤 5씩, 2초 뒤 10씩. 캠프 메뉴는 늘리지 않았다.
- [x] **X6. 확장 규칙: 협공** (새 게임에서 켠 판만)
  - `CampaignState::extended_rules` → `BattleState::extended_rules`. `joint_attack_pct`: 공격받는 유닛과 상하좌우로 붙은 공격자 편
    1명당 +10 %, 최대 +30 %, 반격 제외. 실제 피해·예보(`attack_forecast`)·AI 공격 평가가 같은 값을 쓴다. 예보 창에 `협공 +N%`.
  - 남은 것: 폭(10 %·30 %)은 사람이 해 본 뒤 조정한다. 다른 확장 규칙(상태이상 등)은 요청이 있을 때 D25의 표를 다시 본다.
- 새 게임 메뉴: 타이틀 "새 게임" → 난이도(◀▶)·능력치 자유 조정·확장 규칙(끔/켬)·시작. 커서는 "시작"에 있어 바로 누르면 원작 그대로다.
- [x] **X2. 공개 초상화 토글** (설정 "얼굴: 원작 / 공개 초상화")
  - 기본 팩 `gfx/portraits`의 퍼블릭 도메인 초상화 119장(CREDITS.md; 책에 그 인물이 실제로 그려진 것은 약 52명, 나머지는 대역).
    체인에 `original` 팩이 있으면 그 아래 층에서 같은 키를 먼저 찾고(`DataRoot::public_media_paths`), 없으면 원작 얼굴.
    캐시 키는 `<key>#public`이라 실행 중에 바꿔도 바로 반영된다. 원작 층이 없는 체인(웹, 기본 팩만)에서는 바꿔도 달라지는
    것이 없으므로 설정 행이 "원작 데이터 없음"으로 꺼져 보인다(v0.4.1).
- [x] **X4. 편의: 적 위험 범위** (설정 "위험 범위: 끔 / 켬")
  - 아군 페이즈에 아무것도 고르지 않았을 때, 활동 중인 적 전부의 이동 범위 + 공격 칸을 칠한다(`danger_tiles`). 혼란한 적은
    회복할 수 있으니 전체 이동력으로 센다. 유닛 위치·상태·턴·지형이 바뀔 때만 다시 계산한다(`danger_key`).
- [x] **X5. 연출 강화** (설정 "전투 연출: 원작 / 강화")
  - 피해 숫자는 원래 떠 있었으므로, 강화는 빨간 `-N`과 큰 타격(최대 병력의 25 % 이상이거나 퇴각)의 지도 흔들림(3px, 0.25초,
    전투 속도를 따름)이다.

## H. 사람이 하는 확인

DOSBox 관찰로 **사실**(칸·수치·곡)은 기계로 확인할 수 있다. 하지만 **체감**(난이도, 소리의 자연스러움)은 사람이 확인해야 한다.
원작과 우리 게임을 나란히 띄워 같은 전투를 비교하는 방식이 가장 효율적이다.
원작의 상태 저장 파일과 우리 세이브를 각 전투 직전으로 준비해 두면, 사람은 처음부터 진행할 필요 없이 바로 그 전투로 갈 수 있다.

| 확인 | 준비해 둘 것 | 언제 |
|---|---|---|
| 1장 첫 전투(광천·신도) 난이도 | 두 루트의 전투 직전 세이브(우리), 같은 지점의 원작 상태 저장 | M1 뒤 |
| 서장·1장 통과 | 장별 세이브 | M2 뒤 |
| 장판파 백성 호위 | `c2_s3_b7` 직전 세이브 | 언제든 |
| 2장 난이도 | 1장을 끝낸 세이브 | M1 뒤 |
| 곡 배정과 루프 | M5-4의 기계 비교 결과표 + 장면별 짧은 녹음 | M5 뒤 |
| `advance` AI (서주1·계교) | 전투 직전 세이브 | 언제든 |

각 확인의 결과는 BACKLOG 해당 항목에 날짜와 함께 적고 닫는다.
