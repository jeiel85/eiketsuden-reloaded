# 설계 결정 기록 (Decision Log)

되돌리기 어려운 결정만 기록합니다. 각 항목은 날짜 · 결정 · 검토한 대안 · 근거 순서입니다.

## D1. 언어와 엔진: Rust + macroquad (2026-09-24)

**결정**: 게임 엔진은 Rust로 작성하고 렌더링·입력·오디오는 [macroquad](https://github.com/not-fl3/macroquad) 0.4를 쓴다.
하나의 코드베이스에서 Windows / Linux / macOS 네이티브 실행 파일과 WebAssembly(브라우저) 빌드를 모두 만든다.

| 대안 | 장점 | 탈락 사유 |
|---|---|---|
| C++ + SDL2 + Emscripten (OpenRCT2와 동일) | 원조와 같은 구조 | 툴체인·빌드가 무겁고 웹 빌드 설정 비용이 큼 |
| TypeScript + Canvas + Electron | UI 개발 속도, 웹 우선 | 데스크톱 배포가 100MB+ Electron 번들, "EXE 대체"로서 무거움 |
| Go + Ebitengine | 단순, 크로스 컴파일 쉬움 | 개발 머신에 Go 툴체인 없음, 이점이 Rust 대비 크지 않음 |
| Godot 4 | 에디터·익스포트 완비 | 씬 파일 중심이라 데이터 주도 엔진 재구현과 성격이 다름, 바이너리 큼 |

**근거**: 원작 EXE를 대체하는 "엔진 재구현"(OpenRCT2 방식)이라는 목표에 네이티브 단일 실행 파일이 맞고,
같은 코드로 웹 라이브 데모를 만들 수 있다. 스파이크에서 Galmuri 폰트로 한글·한자 렌더링과
wasm32 빌드(약 630KB)가 브라우저에서 정상 동작함을 확인했다.

## D2. 코드 라이선스: GPL-3.0-or-later (2026-09-24)

**결정**: 엔진 코드는 GPL-3.0-or-later. **근거**: 참조 모델인 OpenRCT2와 같은 라이선스로, 재구현 프로젝트가 폐쇄 포크로 흡수되는 것을 막는다.
에셋은 각자의 라이선스(CC0 / CC-BY / OFL / 퍼블릭 도메인)를 따르며 `CREDITS.md`에 출처를 모두 적는다.

## D3. 에셋 정책: 원작 데이터는 저장소에 절대 포함하지 않는다 (2026-09-24)

**결정**: 저장소와 배포물에는 KOEI TECMO의 그래픽·음악·텍스트·실행 파일을 포함하지 않는다.
기본 콘텐츠("base pack")는 퍼블릭 도메인인 소설 『삼국지연의』를 바탕으로 새로 쓴 시나리오와
CC0 / CC-BY / OFL / 퍼블릭 도메인 에셋만으로 구성한다. 원작 데이터는 사용자가 정품을 보유한 경우에만
사용자 PC에서 읽어 쓰는 선택 기능으로 둔다(OpenRCT2가 RCT2 데이터를 요구하는 방식과 동일).

**근거**: 코드와 콘텐츠가 모두 재배포 가능한 라이선스여야 공개 저장소와 웹 데모가 법적으로 안전하다.
`.gitignore`에 `/data/original/`을 넣어 가져온 원작 데이터가 실수로 커밋되지 않게 한다.

## D4. 데이터 형식 (2026-09-24)

**결정**: 규칙·전투 데이터는 TOML, 대화 장면은 전용 `.drama` 스크립트, 이미지는 PNG, 음악·효과음은 OGG/WAV,

웹과 네이티브에서 같은 파일을 그대로 읽을 수 있다. 세이브 형식은 `version` 필드로 이후 마이그레이션을 허용한다.

## D5. 공개 저장소와 웹 데모 (2026-09-26)

**결정**: 저장소를 public으로 공개하고 GitHub Pages에 웹 라이브 데모를 올린다.

**근거**: 라이선스 점검 결과 공개에 걸림돌이 없다.

* 코드는 전부 새로 작성했다(GPL-3.0-or-later).
* 미디어는 CC0 / CC-BY / OFL / 퍼블릭 도메인만 쓰며 `CREDITS.md`에 출처를 모두 적었다.
* 대사와 시나리오는 퍼블릭 도메인 소설 『삼국지연의』를 바탕으로 새로 썼다.
* 원작에서 KOEI가 창작한 오리지널 무장은 역사 인물이나 이 리메이크의 창작 인물로 바꿨다.

원작의 규칙과 수치는 저작권 보호 대상이 아닌 사실 정보로 보고 재현한다. "영걸전(英傑伝)" 명칭은 OpenRCT2·OpenTTD처럼 원작을 가리키는 설명 목적으로만 쓴다. README에 KOEI TECMO와 무관하다는 고지를 넣고, 로고·트레이드 드레스는 쓰지 않는다.

**대안**: private으로 보관 후 공개(웹 데모 없음). 라이선스 위험이 확인되지 않아 채택하지 않았다.

**변경 (2026-09-30, D21)**: 웹 데모는 내렸다. 브라우저는 사용자의 원작을 읽을 수 없어 기본 팩의 시험 전투밖에 보여 줄 수 없다.
같은 주소(GitHub Pages)에는 게임 없이 프로젝트를 소개하는 정적 페이지(`site/`)를 올린다. 페이지의 스크린샷은 기본 팩의 것만 쓴다.

## D6. 원작 데이터 임포터: 별도 선택 크레이트 + 미디어 오버레이 (2026-09-26)

**결정**: 정품 보유자용 임포터는 게임과 분리된 `crates/hero-import` 라이브러리와 `hero-tools original probe|extract`
명령으로 둔다. 결과물은 사용자가 고른 로컬 폴더에 **미디어 오버레이**(PNG + UTF-8 JSON + `index.json`)로 쓰고,
게임은 `--original <dir>`(네이티브 전용)일 때 미디어를 오버레이 → 팩 순서로 찾는다. 공유용 프로브 매니페스트
(`eiketsuden-original-probe` v1)와 오버레이 인덱스(`eiketsuden-original-overlay` v1)는 `format_version`을 가진
JSON이다. 새 의존성은 `encoding_rs`(EUC-KR/Big5), `sha2`(해시), `png`(이미 macroquad 경유로 잠금 파일에 있음)뿐이다.
자세한 내용은 [ORIGINAL_DATA.md](ORIGINAL_DATA.md).

| 대안 | 탈락 사유 |
|---|---|
| 게임 실행 파일 안에서 원작 파일을 직접 읽기 | 웹 빌드 크기 증가, 파서 오류가 게임 실행 경로에 들어옴, 원작 판본 차이를 매 실행마다 처리해야 함 |
| 원작 데이터를 완전한 데이터 팩으로 변환 | 맵·시나리오·규칙 형식이 아직 규명되지 않아(P4–P6) v1에서 불가능 |
| 사용자 데이터 폴더에 자동 저장 | 출력 위치를 사용자가 명시(`--out`)해야 저장소·설치 폴더에 실수로 쓰는 일을 막기 쉬움 |
| 인코딩 표·해시를 직접 구현 | 검증된 MIT/Apache 크레이트가 더 안전하고 작음 |

**근거**: D3(원작 데이터 비포함) 원칙을 유지하면서 OpenRCT2식 선택 기능을 제공한다. 클린룸(조사 노트의 사실만
사용, 타 프로젝트 코드 미사용), 읽기 전용, 업로드 없음, 복제 방지 우회 금지, 저장소·CI에 원작 바이트 없음(합성
픽스처와 환경 변수로만 도는 골든 테스트)을 지킨다. 문서로 확정되지 않은 형식(TF-DCE 얼굴, `BAKDATA` 배치)은
추측하지 않고 "지원 안 함"으로 보고한다.

## D7. 콘텐츠 라이선스: 기본 팩의 텍스트·데이터는 CC BY-SA 4.0 (2026-09-26)

**결정**: 기본 팩(`data/base`)의 텍스트·데이터 파일 — `pack.toml`, `officers.toml`, `campaign.toml`,
`rules/*.toml`, `battles/*.toml`, `dramas/*.drama`, `credits.txt` — 은
[CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/)으로 배포한다. 엔진·도구 코드는 D2대로
GPL-3.0-or-later, 미디어(`gfx`, `sfx`, `bgm`, `fonts`)는 출처별 라이선스를 따른다. `CREDITS.md`의 "Licences"
표가 이 구분의 기준이고, `pack.toml`의 `license`와 `credits.txt`가 같은 내용을 적는다.

| 대안 | 장점 | 탈락 사유 |
|---|---|---|
| 저장소 전체를 GPL-3.0으로 두기 | 라이선스가 하나 | GPL은 소프트웨어용이라 대사·시나리오를 쓰는 2차 창작(소설, 위키, 다른 게임의 팩)에 조건이 맞지 않고, 이미 `pack.toml`·`credits.txt`가 CC BY-SA 4.0이라 적어 둔 것과 충돌한다 |
| CC BY 4.0 | 재사용 조건이 가장 가벼움 | 개작본이 닫힌 라이선스로 흡수될 수 있어 D2(GPL 선택)의 취지와 어긋난다 |
| CC0 | 제약 없음 | 출처 표시조차 요구할 수 없어 기여자 크레디트가 사라진다 |

**근거**: 텍스트 콘텐츠에 맞는 카피레프트 라이선스로, 코드의 GPL과 같은 "개작도 같은 조건으로" 원칙을 지킨다.
CC BY-SA 4.0은 GPL-3.0과 단방향 호환(CC BY-SA 4.0 → GPLv3)이라 팩 데이터를 GPL 코드에 넣어야 할 때도 막히지 않는다.
공개 전에 파일마다 서로 다른 조건이 보이지 않도록 한 번 정해 두며, 기여자가 늘어난 뒤에는 바꾸기 어렵다.

## D8. 팩 레이어링: `extends`로 다른 팩 위에 얹는 팩 (2026-09-26)

**결정**: `pack.toml`에 `extends = "<상대 디렉터리>"`를 두면 그 팩(부모) 위에 얹히는 자식 팩이 된다. 자식은 자기가
제공하는 파일만 적는다. 규칙 파일 다섯 개·`officers`·`campaign`은 가장 가까운 팩의 것이 **파일 단위로 대체**되고,
전투와 대사 장면은 **모든 팩의 합집합**이며 같은 전투 id·장면 id는 가까운 팩이 덮어쓴다(한 팩 안에서는 여전히
중복 금지). 미디어(`gfx/`, `bgm/`, `sfx/`, `fonts/`)는 최상위 팩부터 부모 순으로 찾고, 미디어 색인 파일도 파일 단위로
대체된다. 경로는 최상위 팩 기준으로 **어휘적으로**(`..`는 앞 구간 제거, URL과 동일) 풀고, 체인은 최대 4개 팩,
순환·없는 부모·체인 안의 같은 팩 `id`는 로드 오류다. 같은 결정의 일부로 `[presentation] canvas = [w, h]`
(기본 480×270, 480×270..1280×800; 처음 최소는 320×200, D13에서 올림)를 두고, `[presentation]`은 **필드 단위**로
상속한다(필드마다 그 필드를 적은 가장 가까운 팩의 값, 없으면 기본값. 2026-09-28 확정, 아래). 세이브는 최상위 팩의
`id`를 기억한다. 규칙은 [MODDING.md](MODDING.md#layered-packs-extends)에 있다.

| 대안 | 장점 | 탈락 사유 |
|---|---|---|
| 완전한 팩만 허용(부모를 통째로 복사) | 규칙이 가장 단순 | 원작 모드·밸런스 모드마다 기본 팩 전체를 복제해야 하고, 기본 팩이 고쳐져도 복제본에 반영되지 않는다. 원작 모드를 에셋 하나씩 늘려 가는 방식이 불가능 |
| D6의 미디어 오버레이만 확장 | 이미 있음, 게임 쪽 변경 없음 | 미디어만 바꿀 수 있어 규칙·맵·시나리오·캔버스 크기를 원작 것으로 바꿀 길이 없다. 오버레이 위치가 팩 밖(실행 옵션)에 있어 팩만 보고는 무엇이 로드되는지 알 수 없다 |
| 모든 파일을 항목 단위로 병합(자식 `items.toml`이 아이템 몇 개만 추가·수정) | 작은 모드에 편함 | 삭제 표현, 순서(지형 표시 순서·승급 체인) 의미, 검증 문맥이 모호해진다. 전투·장면처럼 원래 id 하나가 한 단위인 것만 id 단위로 합치고 나머지는 파일 단위 대체로 한정 |
| 실행 시 여러 팩을 순서대로 지정(`--data a --data b`, 모드 로드 순서) | 조합이 자유로움 | 조합이 팩 밖에 있어 재현·검증·세이브 호환 판단이 어렵고, 웹 빌드에는 명령줄이 없다 |
| 절대 경로·URL `extends` | 어디에 있든 참조 가능 | 팩 폴더를 옮기면 깨지고 웹 빌드(상대 URL fetch)에서 동작하지 않는다. 대신 원작 모드 팩은 기본 팩 옆(`data/original/`)에 두는 것으로 정한다 |
| 체인 깊이 무제한 | 제약 없음 | 순환 오류 메시지가 늦어지고 실사용 사례(원작 모드 위의 모드 정도)는 3단이면 충분. 4로 제한 |
| `[presentation]`을 테이블 단위로 상속(선언한 테이블이 부모 것을 통째로 대체, 빠진 필드는 기본값) | 규칙 파일의 파일 단위 대체와 같은 모양 | 필드를 하나 추가하는 순간, 그 필드를 모르는 기존 자식 팩이 부모 값 대신 기본값을 받게 되어 호환이 깨진다. 빈 `[presentation]`이 부모의 캔버스를 기본값으로 되돌리는 것도 직관에 어긋난다. 필드가 `canvas` 하나일 때 필드 단위로 바꿔 두면 달라지는 경우는 빈 테이블뿐이다 |

**근거**: "원작 모드"(원작 에셋으로 그리는 모드)는 원작 형식이 규명되는 대로 에셋을 하나씩 바꿔 가야 하므로, 아직
변환하지 못한 모든 것을 라이선스 청정 기본 팩에서 가져올 수 있는 구조가 필요하다. 같은 구조가 일반 모드(밸런스
조정, 전투 추가)에도 그대로 쓰인다. 로딩은 웹을 위해 2단계를 유지한다: `pack.toml`을 하나씩 읽어 체인을
완성(`PackChain`)한 뒤 필요한 `(팩 디렉터리, 경로)` 전체를 나열하고, 그 파일들로 `Pack::load`를 호출한다.
`pack.toml` 필드·세이브 호환에 영향을 주는 결정이라 기록한다. `credits.txt`는 체인의 모든 팩 것을 가까운 팩부터
이어 보인다(자식 팩이 부모의 CC BY·CC BY-SA 저작자 표시를 가리지 않도록, 2026-09-28). 전투 화면의 미디어 색인
(`units.toml`·`terrain.toml`·`fx.toml`)도 다른 미디어처럼 파일마다 오버레이 → 최상위 팩 → 부모 순으로 찾는다
(색인과 그 색인이 가리키는 그림은 각자 찾으므로, 크기가 다른 그림을 넣는 팩·오버레이는 색인도 함께 넣는다. 웹에서는
없는 후보마다 fetch 한 번이 실패한다. 처음에는 웹에서 최상위 팩 것만 읽었으나 2026-09-28에 맞췄다).

## D9. 맵 파일과 그림 층 (2026-09-28)

**결정**: 전투 맵에 **그림 층**을 둔다. `[map] image = "<키>"`이면 맵 전체를 그린 그림 한 장
`gfx/maps/<키>.png`를 타일셋 대신 그리고, `rows`는 그대로 **규칙 층**(이동·방어·회복·책략)이다. 그림 크기는 정확히
맵 칸 수 × 타일셋 `tile_size`여야 하며, 없거나 크기가 다르면 게임은 경고를 남기고 타일셋으로 그리고
`hero-tools validate`는 오류로 보고한다. 같은 결정의 일부로 전투와 떨어진 **맵 파일**을 둔다. `pack.toml`의
`maps = [...]` 파일에 `[[map]]`(`id`, `name`, `rows`, `legend`, `theme`, `image`)을 적고, 전투는 `[map] use = "<id>"`로
참조하며 `use`와 다른 맵 필드를 함께 쓸 수 없다. 레이어드 팩에서 맵은 전투·장면처럼 **합집합 + 가까운 팩 우선**이고,
`use`는 체인 전체를 합친 뒤 풀리므로 자식 팩의 맵이 부모 전투의 맵도 바꾼다. `Pack::load`가 `use`를 풀어
전투 정의에 맵을 복사하므로 전투 규칙·세이브·AI는 바뀌지 않는다. 규칙은 [MODDING.md](MODDING.md#map-files),
그림 규격은 [ASSETS.md](ASSETS.md#map-pictures--gfxmapskeypng)에 있다.

| 대안 | 장점 | 탈락 사유 |
|---|---|---|
| 그림 층 없이 타일셋만(학습 타일셋 개선) | 엔진 변경 없음 | 원작 맵은 칩이 대각선·부분 칸으로 이어져 칸 단위 타일로는 같은 그림이 나오지 않는다(BACKLOG "학습 타일셋의 경계 개선"). 원작 맵은 칩 격자 자체가 정답이다 |
| 원작 칩 격자(16 px)를 엔진 맵 격자로 | 칩을 그대로 쓸 수 있음 | 원작의 이동 격자는 2×2 칩 칸(32 px)이라 규칙 격자와 그림 격자가 다르다. 엔진에 두 격자를 들이는 대신 칩을 미리 그림으로 합친다 |
| 그림을 칸 단위 조각으로 자른 아틀라스 | 기존 타일셋 경로 재사용 | 58개 맵이 거의 모든 칸마다 다른 조각을 만들어 아틀라스가 커지고, 맵마다 전용 타일 키가 필요해 지형 규칙과 섞인다 |
| 맵 파일 없이 전투 파일에만 맵 | 형식 추가 없음 | 원작 맵은 시나리오 변환(STATUS 4절 2단계)보다 먼저 변환·검증할 수 있는데, 쓰는 전투가 없으면 팩에 둘 곳이 없다. 같은 맵을 여러 전투가 쓰는 경우에도 복사가 필요하다 |
| 맵 파일 하나에 맵 하나 | 파일이 작음 | 원작 모드가 58개 파일을 쓰게 되고, 드라마 파일처럼 여러 항목을 담는 편이 목록 관리가 쉽다 |
| 쓰지 않는 맵은 경고 | 실수를 찾기 쉬움 | 원작 모드 팩은 전투보다 맵이 먼저 들어가므로 경고 58개가 상시 나온다. 검증은 모든 맵에 똑같이 하되 미사용은 경고하지 않는다 |

**근거**: 원작 모드는 원작 전투를 원작 맵 위에서 해야 하는데(STATUS 4절 1단계 "원작 맵"), 원작 맵의 모습은 칩 격자,
규칙은 칸마다의 지형 바이트다. 이 둘을 그림 층과 규칙 층으로 나누면 엔진은 규칙 격자만 알면 되고, 모드도 손으로 그린
맵 그림을 쓸 수 있다. `pack.toml` 필드와 전투 형식에 영향을 주는 결정이라 기록한다. 세이브에는 맵 격자(`BattleMap`)만
저장되고 그림은 전투 정의에서 오므로 세이브 형식은 바뀌지 않는다.


## D10. 원작 모드는 게임 안에서 폴더를 고르고, 실행할 때마다 메모리에서 변환한다 (2026-09-28)

**결정**: 원작 모드를 OpenRCT2처럼 쓴다(이슈 #5). 플레이어는 타이틀의 "원작 데이터"에서 **게임 안 폴더 탐색기**로
원작 설치 폴더를 고르고, 게임은 경로와 "원작 모드 켬"을 설정(`settings.json`의 `original_dir`, `original_mode`)에
기억한다. 실행할 때마다 로딩 화면이 기본 팩을 읽은 뒤 `hero_import::pack::build_pack`으로 원작 모드 팩을 **메모리에서**
만들고(작업 스레드), 그 파일들을 기본 팩 옆 디렉터리(`<data>/original`)에 **마운트**해(`hero-game`
`platform/memfs.rs`) 레이어드 팩 체인을 디스크에서와 똑같이 읽는다. 마운트 디렉터리 안의 경로는 메모리에서만 읽고
(같은 이름의 디스크 폴더는 무시), 밖의 경로는 `..`를 어휘적으로 풀어(D8과 같은 규칙) 디스크에서 읽는다. 디스크에는
아무것도 쓰지 않는다. 그 결과 `hero-game`이 `hero-import`에 **네이티브 전용으로** 의존하고(웹 빌드에는 들어가지 않음),
`hero-import`는 기본 팩에서 변환 옵션을 만들기 위해 `hero-core`에 의존한다(`PackOptions::for_pack`). `--data` /
`EIKETSUDEN_DATA`로 팩을 지정하면 그 팩이 우선하고 원작 모드 설정은 적용되지 않는다. 폴더 없음·미지원 판본·변환
실패·변환된 팩의 로드 실패는 원인을 보여 주는 화면으로 끝나고 다시 시도·다른 폴더·기본 팩으로 계속을 고를 수 있다.
`hero-tools original pack`(파일로 쓰기)은 개발·검증용으로 남긴다.

| 대안 | 장점 | 탈락 사유 |
|---|---|---|
| (B) 처음 연결할 때 변환해 사용자 데이터 폴더에 캐시 | 실행 때 변환 시간 없음 | 한국어 DOS/V 실물 변환이 release 빌드 약 0.12초(debug 약 1.2초)라 이득이 없다. 원작에서 변환한 그림이 디스크에 남고(공유 위험), 원작 파일·변환기 버전이 바뀌었는지 판정하는 무효화 규칙이 필요하며, 사용자 데이터 폴더와 기본 팩이 다른 드라이브면 상대 `extends`(D8)로 이을 수 없어 체인 규칙을 바꿔야 한다 |
| OS 기본 폴더 대화상자(`rfd` 등) | 익숙한 UI, 경로 붙여넣기 | Linux에서 GTK3 개발 라이브러리나 xdg-portal(zbus·async 런타임)이 필요해 빌드·CI 의존성이 커지고, 게임 창·전체 화면과 따로 논다. 게임 안 탐색기는 의존성 없이 세 OS에서 같고, 원작 파일이 있는 폴더를 ★로 표시하고 판본 판정·근거를 바로 보여 줄 수 있다 |
| 게임 안 경로 입력 칸만 | 구현이 작음 | 경로를 외워서 쳐야 해 불편하고, 한글 경로 입력(IME)이 필요하다. 탐색기 + 글자 이동으로 대신한다(경로 입력은 BACKLOG) |
| 가상 파일 계층 대신 `DataRoot`에 메모리 레이어 타입 추가 | 전역 상태 없음 | 파일 읽기가 모두 `DataRoot`가 만든 문자열 경로를 받는 구조라(`FileRequest`, 전투 색인, 제작진) 호출부를 모두 바꿔야 한다. 마운트는 읽기 한 곳(`assets::fetch`)만 바꾸고 체인·검증·미디어 코드는 그대로 둔다(처음에는 `DataRoot::path`의 존재 확인도 바꿨으나, 미디어가 모두 `media_paths` 후보를 차례로 읽게 되어 2026-09-28에 없앴다) |

**근거**: 원작 모드의 목표가 OpenRCT2와 같은 경험(명령줄 없이, 원작 파일이 있으면 원작 모드, 없으면 없음)이고, 변환이
충분히 빨라 캐시 없이도 로딩 화면 안에서 끝난다. 원작 데이터를 디스크에 남기지 않는 것이 D3(원작 데이터 비포함)의
취지에도 맞다. 새 외부 의존성은 없고(`hero-import`는 이미 작업 공간 크레이트), 설정 파일 필드 두 개가 추가된다
(모르는 필드·빠진 필드는 기본값이라 이전·이후 빌드와 호환). D6의 "게임 실행 파일 안에서 원작 파일을 직접 읽기"를
탈락시킨 사유(웹 빌드 크기, 파서 오류가 게임 경로에 들어옴)는 네이티브 전용 의존과 작업 스레드 격리(패닉도 오류
화면으로 보고), 변환 실패 시 기본 팩으로 계속하는 경로로 해소한다. 미디어 오버레이(`--original`)는 추출물을 살펴보는
용도로 그대로 둔다.

## D11. 원작 전투는 기본 팩 전투를 원작대로 다시 짠다 (2026-09-28)

**결정**: 원작 모드의 첫 원작 전투는 원작 시나리오를 통째로 변환하지 않고, **기본 팩의 전투(같은 id)를 원작의 같은
전투대로 다시 짠 전투 파일**로 대체한다. 기본 팩 서장·1장 21개 전투마다 원작 전투를 대응표로 짝짓고(`hero-import`
`battles.rs`, 두 경로가 같은 원작 전투를 쓰는 계교·하비 포함), 원작에서 맵·턴 제한·배치 칸·적과 우군 명단·보물·목표
칸·증원과 그 합류 조건을 가져오며, 이름·목표 문구·전후 대사 장면·음악·보상·캠페인 흐름과 여전히 맞는 기본 팩 이벤트는
기본 팩 것을 쓴다. 기본 팩이 원작 인물의 자리를 다른 인물로 바꾼 곳은 역할 대응표로 잇는다. 옮기지 못한 것은 전투마다
기록한다. 같은 결정의 일부로 엔진의 `reach` 조건·트리거에 선택 필드 `to`(직사각형)를 추가한다: 원작의 영역 트리거
(종류 11)를 그대로 표현하기 위한 것으로, 기존 데이터에는 영향이 없다.

| 대안 | 장점 | 탈락 사유 |
|---|---|---|
| 원작 캠페인 전체(마을·대사·분기)를 변환한 별도 캠페인 | 원작과 가장 같음 | 마을 장면·대사 변환(`SNRnM`)과 원작 이벤트 전체 변환이 선행돼야 해 한참 뒤에야 플레이할 수 있고, 기본 팩의 캠페인·세이브·플래그와 따로 놀게 된다. 이 결정의 결과물(전투 파일)은 그 캠페인에서도 그대로 쓸 수 있다 |
| 기본 팩 전투의 맵만 원작 맵으로 교체(`use`만 바꿈) | 가장 작음 | 기본 팩의 배치 좌표가 원작 맵에서 벽·강 위에 떨어져 검증을 통과하지 못한다 |
| 원작 영역 트리거를 원(맨해튼 반경)으로 근사 | 엔진 변경 없음 | 영역이 달라져 증원이 나오는 시점이 원작과 달라진다. 선택 필드 하나로 정확히 표현할 수 있다 |
| 원작 전투 중 이벤트까지 한 번에 변환 | 완성도 | 일기토 연출·AI 전환·영입·대체 승리마다 엔진 이벤트와의 대응을 정해야 해 범위가 크다. 배치와 증원만으로도 원작 맵에서 원작 전투를 할 수 있어 먼저 낸다(STATUS 4절 2단계) |

**근거**: 원작 모드의 목표는 원작 화면에서 원작 전투를 하는 것이고, 기본 팩은 원작 PC판 전투를 따라 설계돼 있어 전투
단위로 짝이 맞는다. 원작에서 확정된 사실(좌표축·맵 번호·합류 바이트·보물 칸, FORMATS §13)만 쓰고, 추론인 것(당시 AI 0·5·6, 뒤에 `MAIN.EXE`로 확정)은
표시한다. 원작 데이터가 없으면 이 파일들도 없으므로 기본 팩은 그대로다.

## D12. 원작 전투 중 이벤트는 원작 대사로, 단계와 조건으로 옮긴다 (2026-09-28)

**결정**: 원작 모드 전투(D11)의 전투 중 이벤트를 원작 트리거 레코드에서 변환한다. 전투 블록의 그룹 3부터를 **단계**로
보고, 엔진에 세 가지를 더한다: 이벤트의 `stage`와 동작 `set_stage`(단계), 이벤트의 `when`(플래그 조건, 캠페인 분기 노드와
같은 `{ flag, cmp, value }`), 동작 `set_terrain`(칸 하나의 지형과 그 칸 그림). 대사·안내문·일기토는 **사용자 사본에서
읽은 원작 대사**로 대사 장면을 만든다. 기본 팩이 같은 계기(같은 턴·같은 두 유닛의 인접·같은 유닛의 격파)의 이벤트를 유지하면
그 이벤트가 이야기를 맡고, 원작 레코드의 나머지 동작(퇴장·단계 넘김·승리)을 거기에 더한다. 경로 플래그와 한 번만 실행하는
플래그는 변환할 때 판정하고, 레코드 사이에 공유되는 플래그만 전투 플래그(`orig_<전투>_<번호>`)가 된다. `set_map_chip`의
뜻(성문·적교)은 `MAIN.EXE`를 읽어 정하고 표는 코드 서명으로 사용자 실행 파일에서 찾는다(FORMATS §13.5).

| 대안 | 장점 | 탈락 사유 |
|---|---|---|
| 기본 팩 이벤트만 유지(지금까지) | 변환 없음 | 원작 맵 위에서 원작 전투의 증원 외 흐름(AI 전환, 성문, 적교, 대체 승리)이 없어 하비는 성에 들어갈 수 없다 |
| 원작 바이트코드를 실행 중에 해석 | 원작과 같음 | 엔진이 KOEI 형식에 묶이고, 원작 없는 기본 팩·모드와 다른 실행 경로가 생긴다(D8·STATUS 4절의 원칙) |
| 단계 대신 플래그로 모든 흐름 표현 | 엔진 변경이 하나 | 단계 넘김마다 플래그 조건을 여러 이벤트에 반복해 써야 하고, 원작 그룹 구조가 파일에서 보이지 않는다 |
| 원작 이벤트가 기본 팩 이벤트를 항상 대체 | 원작에 더 가까움 | 기본 팩이 자기 말로 쓴 일기토 장면과 캠페인 플래그(`sishui_duel` 등, 전후 장면이 읽음)가 사라진다 |

## D13. 가장 작은 가상 캔버스는 480×270이다 (2026-09-28)

**결정**: `[presentation] canvas`의 하한을 320×200에서 **480×270**(기본값과 같음)으로 올린다. 더 작은 캔버스를 적은
팩은 로드 오류이고, 지금까지 이를 경고하던 validate 검사는 없앤다.

| 대안 | 장점 | 탈락 사유 |
|---|---|---|
| 320×200까지 허용하고 경고만(지금까지) | 변경 없음 | 허용한 크기에서 캠프·전투 화면이 겹치고 잘린다. 허용하는 설정은 제대로 동작해야 한다 |
| 480×270 미만용 캠프·전투 레이아웃을 따로 만든다 | 작은 캔버스 지원 | 캠프 허브·부대 편성·장비·상점·도구·무장 정보·전투 상단 막대 등 아홉 화면을 다시 짜야 한다(320×200에서 확인). 그런데 그 크기를 쓰는 팩이 없다(기본 팩 480×270, 원작 모드 640×480). 확인된 요구 없이 유지할 화면만 늘어난다 |
| 작은 캔버스에서 480×270으로 그려 축소 | 코드가 적음 | 비정수 축소로 픽셀 글꼴(12px·10px)이 뭉개져 읽을 수 없다 |

**근거**: 가상 캔버스는 해상도가 아니라 레이아웃 크기다. 실제 창이나 휴대폰 화면이 작으면 렌더러가 캔버스를 비율대로
줄인다(`gfx.rs`). 그래서 작은 캔버스는 작은 기기를 위한 것이 아니고, 쓸 팩도 없다. 저장소와 릴리스에 든 팩(기본 팩,
원작 팩 변환 결과, 테스트 픽스처)은 모두 그대로 로드된다. v0.1.0 문서를 따라 480×270보다 작은 캔버스를 적은 외부 팩은
로드 오류(범위를 적은 메시지)가 되고 그 팩의 세이브도 열 수 없다. 알려진 사례는 없고, 다음 릴리스 노트에 팩 형식 변경으로
적는다. 나중에 작은 캔버스가 필요한 팩이 생기면 그때 레이아웃을 만들고 하한을 다시 내리면 된다(하한을 내리는 쪽은
호환이 깨지지 않는다).

## D14. 리눅스의 클립보드 읽기는 arboard로, 작업 스레드에서 한다 (2026-09-29)

**결정**: 원작 폴더 탐색기의 붙여 넣기(Ctrl+V)는 리눅스에서 `arboard`(기본 기능 끔, X11)로 작업 스레드에서 읽는다.
다른 플랫폼은 지금처럼 miniquad의 `clipboard_get`을 쓴다. 의존성은 `cfg(target_os = "linux")`에만 붙는다.

| 대안 | 장점 | 탈락 사유 |
|---|---|---|
| miniquad `clipboard_get`(지금까지) | 의존성 없음 | X11에서 `SelectionNotify`가 올 때까지 `XNextEvent`로 기다려, 소유자가 답하지 않으면 게임이 멈춘다. 게임 창의 X11 연결을 쓰므로 다른 스레드로 옮길 수 없다 |
| miniquad를 고쳐 `[patch]`로 들여오기 | 의존성 추가 없음 | 창·입력 계층 전체를 저장소에 두고 따라가야 한다. 기다리는 동안 다른 이벤트를 삼키는 문제도 같이 고쳐야 한다 |
| `xclip`·`xsel` 같은 외부 명령 | 의존성 없음 | 설치되어 있지 않으면 결국 miniquad로 돌아가야 한다 |

**근거**: `arboard`는 자기 X11 연결(x11rb, 순수 Rust)을 열어 어느 스레드에서나 읽을 수 있고, 소유자가 답하지 않으면 4초 뒤
포기한다(3.6의 `LONG_TIMEOUT_DUR`, 텍스트 형식 여섯 가지를 차례로 물으므로 최대 약 24초이고, 시간 초과는 빈 클립보드로
보인다). 폴더 읽기와 같은 작업 스레드 틀(`original::Background`)을 쓰므로 그동안 화면이 그려지고 Esc로 바로 취소할 수 있다.
miniquad 0.4의 리눅스 백엔드는 X11 전용이라 게임이 XWayland에서 돌고, 클립보드도 XWayland로 읽는다(`wayland-data-control`
기능은 켜지 않는다). 범위는 리눅스뿐이다: 다른 X11 유닉스(BSD)는 배포 대상이 아니라 miniquad 읽기를 그대로 쓴다.
되돌리려면 `read_clipboard`의 리눅스 판과 `READS_IN_BACKGROUND`의 리눅스 값(miniquad 읽기는 메인 스레드에서만 해야 한다),
Cargo.toml의 의존성을 함께 지운다.

## D16. 원작 음악은 변환할 때 자체 OPL2 에뮬레이터로 WAV로 렌더링한다 (2026-09-29)

사인·지수 표와 엔벨로프 속도 표(MAME·Nuked OPL 프로젝트가 문서화한 사실)를 따라 새로 작성했다. 곡 배정은 시나리오의

**근거**: 캠페인 파일은 레이어에서 통째로 바뀌므로(MODDING) 원작 모드가 자기 캠페인을 가질 수 있고, 기본 팩이 바뀌면 다시
변환해 따라간다. 노드·장면·전투 id는 새로 생기는 것이라 기존 세이브는 그대로 읽힌다. 이야기의 선형화는 [추론]이라
빠지는 것(잡담, 군에 없는 무장의 레벨·병종 변경, 장 제목 그림)을 `original-pack.json`에 남긴다.

## D19. 원작 책략 식은 게임 규칙 한 필드로 고른다 (2026-09-30)

**결정**: `rules/game.toml`에 `strategy_formulas = "engine" | "original"`(생략 = `engine`)을 두고, `original`이면 전투가
원작 `MAIN.EXE`의 책략 식을 쓴다(RULES §5·§6: 혼란 명중 나눗수 2와 기간 없는 혼란·풀림 굴림(사기가 오를 때도),
사기가 30 미만으로 떨어질 때의 혼란(페이즈 시작의 저사기 혼란 대신, PR #67), 지원 보너스
`LV × INT / 20`과 10 % 난수, 사기 지원 `+ LV / 10`, 최소 피해 없음, 피해 난수 `rand(D / 50)`(상한 미만), 회복 아이템의
10 % 난수(PR #66)). 원작 모드 팩은 책략 규칙을 옮길 때 체인의 게임
규칙을 복사해 이 필드만 바꿔 쓴다.

**대안**: (A) 책략마다 식을 고르는 필드 — 식이 책략이 아니라 전투 규칙(혼란의 풀림, 사기 저하 혼란)에 걸쳐 있어 맞지
않는다. (B) 식의 계수(나눗수·보너스 나눗수·혼란 확률)를 모두 규칙 숫자로 — 원작의 식은 모양 자체가 달라(기간 대신 풀림
굴림, 저사기 반감 없음) 숫자만으로는 표현되지 않고, 쓰이지 않을 조합이 늘어난다.

**근거**: 원작 모드의 목표는 원작 재현이고, 기본 팩은 지금의 엔진 식을 그대로 둔다(기본값). 게임 규칙 파일을 통째로
복사하므로 기본 팩의 게임 규칙이 바뀌면 원작 팩이 가리지만, 디스크에 쓴 팩은 기본 팩 지문으로 알리고(PR #61) 게임 안
원작 모드는 실행마다 새로 변환한다. 원작의 명중 굴림 `rand(P_c) > P_t / 4`는 엔진의 확률식과 거의 같은 값이라 그대로 둔다.

## D20. 순간 저장은 화면이 아니라 '위치'를 저장한다 (2026-09-30)

**결정**: F5(저장)·F9(불러오기)로 언제든 쓰는 순간 저장 칸(`SaveSlot::Quick`, 키 `save_<팩 id>_quick`)을 둔다. 화면(위젯·타이머)은
직렬화하지 않고, 이미 직렬화되는 것들의 위치만 세이브에 더한다. (1) 캠페인·전투는 원래 세이브와 같다(전투 상태는
애니메이션보다 앞서 있으므로 그대로 저장하고 불러올 때 `Scene::sync`로 맞춘다). (2) 드라마 장면은 `DramaRunner`(장면·
`pc`·대기 중인 선택지)와 무대를 만든 단계 목록(`SceneResume::stage`, 배경·그림·화면 어둡게·초상·일기토를 겹치는 것끼리
줄여서)과 화면에 떠 있던 단계를 저장한다. 불러오면 러너를 그 자리에 놓고 무대 단계만 즉시 다시 적용한다. 장면의
부작용(`@set`·`@gold`·`@item`·`@join`)은 저장된 캠페인에 이미 들어 있으므로 장면을 처음부터 다시 돌리지 않는다.
(3) 전투 연출이 큐에 넣었지만 시작하지 않은 드라마 장면은 `pending_scenes`로 저장하고, 불러온 뒤 전투가 이어지기 전에
보여 준다(전투 상태는 이미 그 장면을 지나 있어서 다시 나오지 않기 때문). (4) 새 전투의 제목 카드·목표 창처럼
`begin`이 아직 안 돈 때는 전투를 저장하지 않고 캠페인 노드만 저장해 처음부터 시작한다. 장면 기록이 들어간 세이브만
`version`을 2로 적어 옛 판이 거절하게 한다(옛 판이 부작용이 이미 적용된 장면을 처음부터 다시 돌리면 금·물건이 두 번
들어간다). 나머지 세이브는 1로 남아 옛 판도 읽는다. (5) 같은 이유로 장면 기록은 **같은 버전의 데이터 팩에서만**
이어 하고(`SaveGame::check_resume`: `pack_version`이 같고, 장면이 아직 있고 위치가 장면 안이고, 캠페인 노드가 그 장면을
재생하는 노드일 것), 하나라도 어긋나면 노드의 처음부터 다시 시작하지 않고 **불러오기를 거절**하고 이유를 알린다. 저장된
캠페인에는 위치 앞 단계의 부작용이 이미 들어 있어서 처음부터 다시 돌리면 두 번 적용되고, 바뀐 장면의 같은 `pc`가
다른 명령일 수도 있기 때문이다. (이후 ROADMAP M7-4: 장면 기록은 그 장면의 지문(`Scene::fingerprint`, 명령과 라벨)을 함께
적어, 팩 버전이 달라도 지문이 같으면 이어 한다. 지문이 없는 옛 기록은 전처럼 같은 버전이어야 한다. 순간 저장은 이후 네 칸이 되었고
(M7-3), F5·F9는 설정에서 고른 칸을 쓴다. 1번 칸은 예전 한 칸의 저장 키를 그대로 쓴다. 장면 기록은 이후 진행 중이던 시간 있는 단계도 적는다(`SceneResume::playing`, M7-2):
`@wait`의 남은 시간, 화면 어둡게의 정도(그 정도에서 이어서 바뀜), 일기토 동작(처음부터 한 번 더). 대안 (A)의 부담을 피하려고 화면
타이머 전체가 아니라 이 셋의 진행 정도만 적는다. 전투 연출은 그 뒤에 따로 적는다(`SaveGame::battle_replay`): 연출이 아직 끝나지 않은
첫 행동 직전의 전투 상태와 그때부터의 전투 이벤트다. 불러오면 그 상태로 유닛을 그린 뒤 이벤트의 연출을 처음부터 다시 틀고, 전투 상태는
저장된 결과 그대로다. 화면의 그림 상태가 아니라 이미 직렬화되는 엔진 값만 적으므로 대안 (A)의 부담이 없다. 그 연출 묶음의 드라마 장면이
이미 시작됐으면 두 번 나오지 않도록 예전처럼 끝난 상태로 적는다.) 게임 중 F9는 토스트만 띄우고 진행 중인 게임을 그대로 둔다. (6) 저장 시각이 1초 단위라
같은 초의 저장끼리는 동률이므로 `latest`는 동률에서 순간 저장 → 자동 기록 → 수동 기록 순으로 고른다(순간 저장은 노드에
도착해 자동 기록이 쓰인 뒤의 키 입력으로만 쓰이므로 동률이면 더 새것이다).

**대안**: (A) 화면 전체 스냅샷(무대·대사창·애니메이션 타이머까지 serde) — 화면 구조체마다 직렬화 형식과 그림 자원 참조를
유지해야 하고, 화면을 고칠 때마다 옛 저장이 깨진다. (B) 장면을 처음부터 결정적으로 다시 돌려 N번째 단계에서 멈추기 —
캠페인을 장면 시작 시점으로 되돌려 저장해야 하고, 저장 크기와 재생 시간이 장면 길이에 비례하며, 부작용 적용 순서를
러너와 저장 사이에서 두 벌로 관리하게 된다. (C) 대화·이벤트 중에는 저장을 막고 직전 안정 지점만 저장 — 요청("대화 중에도")과
맞지 않는다.

**근거**: 드라마 러너는 이미 `Serialize`(주석: 장면 도중 저장을 위해)이고, 전투 상태는 액션마다 캠페인과 함께 동기화되어
있어 새로 직렬화할 것이 '무대를 만든 단계'뿐이다. 무대 재현은 `Stage::apply` 한 곳을 재생 중과 복원 중이 함께 쓰고,
테스트가 기본 팩의 모든 장면에서 매 단계마다 '재생한 무대 == 복원한 무대'를(hero-game `drama.rs`), 시험용 팩의 `oath` 장면을
모든 단계에서 잘라 저장·불러와 이어 가도 남은 단계와 최종 캠페인이 그대로 이어 가는 것과 같음을 두 선택지 모두에서
확인한다(hero-core `tests/quick_save.rs`). 저장 칸을 따로 두어 자동 기록·수동 기록을 덮지 않고,
'이어하기'는 가장 최근 것을 고르므로 순간 저장이 더 새로우면 그것을 쓴다. F1~F10은 웹 런타임(miniquad 0.4.11 `js/gl.js`
`canvas.onkeydown`)이 `preventDefault`하므로 브라우저의 F5 새로고침과 겹치지 않는다(코드로 확인했고, 브라우저에서 눌러
본 것은 아니다).

**한계**: 진행 중이던 `@wait`·화면 어둡게의 남은 시간, 일기토 동작의 진행 정도는 저장하지 않고 끝난 상태로 불러온다
(BACKLOG). 데이터 팩 버전이 바뀌면 장면 도중의 순간 저장은 불러올 수 없다(거절 메시지가 뜬다). 새 판으로 올린 뒤에는 그
장면을 처음부터 다시 보거나 다른 기록을 불러와야 한다. 팩 내용을 고치고 `pack.toml`의 `version`을 올리지 않으면 버전
검사는 통과하고, 그때는 장면·위치·노드 검사(`SceneResume::fits`)가 마지막 안전장치다.

## D21. 프로젝트의 본체는 원작 모드다: 기본 팩은 콘텐츠를 더 늘리지 않는다 (2026-09-30)

**결정**: 이 프로젝트의 목표는 OpenRCT2처럼 **사용자가 가진 원작을 현대 시스템(Windows·macOS·Linux)에서 원작대로 돌리는
것**이다. 새 게임을 만드는 것이 아니다. 그래서 다음처럼 정한다.

1. **원작 모드가 본체다.** README·ENGINE의 소개와 진행 상황은 원작 모드를 기준으로 쓴다. 진행률은 "원작의 무엇을
   원작 파일에서 재현하는가"로만 잰다.
2. **기본 팩(`data/base`)은 콘텐츠를 더 늘리지 않는다.** 기본 팩 제2장 이후 캠페인·IF 루트·새 대사는 만들지 않는다
   (BACKLOG의 "이후 콘텐츠 제작"은 취소). 기존 서장·1장은 원작 모드가 아직 기대는 부분이 있어 당장 지우지 않는다.
3. **원작 모드가 기본 팩 콘텐츠에 기대는 곳을 원작 변환으로 바꾼다.** 서장·1장 이야기와 전투는 2–4장처럼 원작 시나리오
   (`SNR0*`·`SNR1*`)에서 직접 만들고(D11·D18의 "기본 팩 전투를 다시 짜는" 방식을 대체), 무장 능력치는 `BAKDATA`에서
   가져온다. 이것이 끝나면 D18의 "기본 팩 캠페인 뒤에 원작 장을 잇는다"도 "원작 캠페인 전체를 원작 모드가 만든다"로 바뀐다.
4. **그다음 기본 팩을 줄인다.** 엔진이 원작 없이 돌아가는 데 필요한 최소 틀(규칙 기본값, 폰트, 원작 화면 틀이 없는 화면의 UI,
   효과음, 테스트·CI용 시험 전투)만 남긴다. 원작 모드는 계속 레이어드 팩(D8)이라, 원작에서 아직 변환하지 않는 종류는 이 틀에서 온다.

**웹 데모(D5, 2026-09-30 정함)**: 브라우저는 사용자의 로컬 원작 폴더를 읽을 수 없어(D10) 웹에서는 기본 팩만 돈다. 4단계에서
기본 팩을 줄일 때 웹 데모(GitHub Pages 배포와 README의 웹 링크)를 **내린다**. 그 전까지는 지금처럼 기본 팩 서장·1장으로
배포한다. 엔진 체험용 최소 데모로 남기는 안은 원작 없이 보여 줄 콘텐츠가 없어 택하지 않았다.

| 대안 | 장점 | 탈락 사유 |
|---|---|---|
| 지금처럼 기본 팩과 원작 모드를 나란히 키운다 | 원작 없이도 끝까지 플레이 | 목표(원작을 현대 시스템에서)와 다르고, 새로 쓰는 콘텐츠(전투·대사·그림)가 원작 재현 작업과 같은 시간을 나눠 쓴다 |
| 기본 팩을 지금 바로 지운다 | 목표가 코드에 바로 드러난다 | 원작 모드가 서장·1장 이야기와 전투 뼈대, 무장 명단과 능력치(`officers.toml`), 규칙 파일 원본, 폰트·효과음을 기본 팩에서 가져오므로(ORIGINAL_DATA 4.5절, 변환기 `pack.rs`는 이 파일들을 쓰지 않음) 원작 모드가 함께 깨진다. CI의 검증·시뮬레이션도 기본 팩으로 돈다 |
| 원작 형식을 엔진이 직접 읽는다(OpenRCT2처럼) | 원작과 가장 같다 | 엔진이 KOEI 형식에 묶이고, 변환해 팩으로 얹는 지금 구조(D8·D10)를 다시 만들어야 한다. 원작 파일을 필수로 읽는다는 목표는 변환 방식으로도 이룰 수 있다 |

**근거**: 원작 모드는 이미 원작의 전투 60개를 모두 원작 데이터로 만들고 2–4장 이야기를 원작에서 변환해 엔딩까지 잇는다
(README 진행 상황). 남은 기본 팩 의존은 서장·1장과 몇몇 표뿐이라, 그 부분을 원작 변환으로 바꾸는 것이 기본 팩에 새 장을
쓰는 것보다 목표에 가깝다. 저장소와 배포물에 원작 데이터를 넣지 않는다는 D3는 그대로다. 원작은 계속 사용자의 PC에서만
읽는다.

**무장 (추가, 2026-09-30)**: 원작 모드 팩은 체인의 무장을 모두 옮긴 `officers.toml`을 쓴다(`officers`는 파일째 바뀌므로 복사가

체인 것으로 둔다. 원작은 합류할 때 시나리오가 병종·레벨을 덮어써서(FORMATS §14) `BAKDATA`의 초기값이 합류할 때의 값이 아니기
때문이다(합류 명령의 값을 읽는 것은 BACKLOG). 변환하는 장에서 유비군에 합류하는 원작 인물 중 체인 무장이 맡지 않는 사람은 `orig_p<BAKDATA 번호>`
무장으로 더한다(모든 값과 얼굴이 `BAKDATA`·`FACEDAT`). 전에는 이런 인물의 합류(`@join`)가 빠졌다. 기본 팩이 만든 인물은 기본 팩
전투가 체인에 남아 있어 명단에서 뺄 수 없으므로 그대로 둔다(BACKLOG). 대안으로 원작의 모든 인물(384명)을 무장으로 만드는 것은
일반 유닛(병사·민중 이름)까지 무장이 되어 민중 처리(D18)와 한 전투에 한 번만 나오는 무장 규칙이 바뀌므로 택하지 않았다.

**서장·1장 (추가, 2026-09-30)**: 원작 모드 캠페인은 `SNR0`(서장)부터 원작의 이야기와 전투로 전체를 만든다(`CHAPTER_FILES`
0–4, `chapters::original_campaign`). 체인 캠페인에서는 제목·시작 무장·시작 금·시작 아이템만 가져온다(시작 무장은 유비·관우·장비로
원작과 같다). 첫 상점은 서장이 첫 전투 전에 정한다. 기본 팩 서장·1장 전투 21개를 원작 맵 위로 다시 짜는 변환(D11)은 계속한다:
캠페인은 그 전투를 틀지 않지만 기본 팩 전투는 체인에 남아 원작의 규칙·맵과 함께 검증되므로(D8), 기본 맵 그대로 두면 원작 지형
비용에서 배치 칸이 막힐 수 있다. 그래서 검증은 "캠페인이 쓰지 않는 전투" 경고 21개를 낸다(기본 팩을 줄이는 4단계에서 사라짐).
원작 모드의 옛 세이브 중 기본 팩 노드에 있던 것은 불러오지 못한다(2–4장 노드는 id가 같다). 이 변환은 원작 파일이 없는
환경에서 합성 데이터로만 시험했다(BACKLOG: 실물 확인).

**무장의 병종·레벨·장비와 일반 유닛 (추가, 2026-09-30)**: 위 "무장" 항목에서 병종·레벨·장비를 체인 것으로 둔 것은 서장·1장이
기본 팩 이야기라 합류 때의 병종 변경·레벨 증가가 재생되지 않았기 때문이다. 이제 캠페인 전체가 원작 이야기이고, 합류 때 원작이
바꾸는 병종·레벨은 `set_class`·`add_levels`뿐이며 둘 다 `@class`·`@level`로 옮겨진다(`set_allegiance`는 소속만 바꿈, FORMATS §14).
그래서 대응되는 무장도 `BAKDATA`의 병종·레벨·장비(무기·병법서·말, 칸마다 첫 것)를 쓴다. 팩에 없는 병종은 체인 것을 두고, id·이름·
얼굴·소개·군주 여부는 체인 것이다. 군에 없는 무장의 레벨 변경이 빠지는 한계(BACKLOG "원작 장 변환의 빠진 부분")는 그대로다.
원작 전투의 일반 유닛(팩 무장이 맡지 않는 인물)은 그 인물의 무력·지력·통솔을 `UnitSpawn.stats`로 가진다. 전에는 병종의 일반
능력치(`generic`)였는데, 원작은 모든 유닛이 `BAKDATA` 인물이라 능력치가 인물마다 다르다.

**4단계: 기본 팩 줄이기와 웹 데모 내리기 (추가, 2026-09-30)**: 기본 팩(0.3.0)에서 이야기 콘텐츠를 지웠다. 서장·1장의 대사 장면
119개, 전투 20개, 캠페인 86노드가 빠지고, 사수관 전투(`p1_sishui`)와 그 장면 넷, 원작 모드를 안내하며 조작을 알려 주는 짧은 장면
(`test_opening`)이 남는다. 캠페인은 안내 → 사수관 캠프 → 전투 → 끝이고, 제목·시작 무장(유비·관우·장비)·시작 금은 원작 모드가
그대로 가져간다. 남긴 것과 그 이유:
- 규칙 파일 다섯, 무장 명단(`officers.toml`): 원작 모드가 원작 값으로 바꿔 쓰는 틀이고, 무장 명단은 원작 인물을 이름으로 짝지어
  얼굴·id를 준다.
- 미디어(그림·음악·폰트·효과음): 원작 모드가 변환하지 않는 그림·소리, 원작 곡 렌더링 전의 음악(D16), 대응 없는 무장의 얼굴, 캠프
  화면의 배경이다. 에셋 파이프라인이 출처를 고정해 바이트까지 재현하므로(`build.py --check`의 고아 검사), 미디어를 지우는 것은
  파이프라인 단계·출처 목록·크레딧과 함께 따로 한다. 폰트의 한자 목록은 지운 대사에만 쓰인 한자가 없어 바뀌지 않는다.
- 시험 전투 하나: 원작 없이 엔진을 시험하고, 게임·도구의 테스트와 CI(`validate`·`simulate`)가 쓴다. 원작 모드는 이 전투도 원작
  맵 위로 다시 짠다(D11, 캠페인은 쓰지 않음).
웹 데모 워크플로(`pages.yml`)는 지웠다. 같은 주소에는 새 `pages.yml`이 정적 소개 페이지(`site/`)를 올려 옛 데모를 덮어쓴다(D5 변경 메모). 웹
빌드(`tools/web`, CI의 wasm 빌드)는 엔진이 계속 웹에서 빌드되는지 지키려고 남긴다. 기본 팩 버전이 바뀌어 옛 세이브·순간 저장
중 지운 노드·장면에 있던 것은 불러오지 못한다.

## D22. 원작은 공식 에뮬레이터에서 관찰용으로만 실행한다 (2026-10-01)

**결정**: v0.2.1까지는 원작 실행 파일을 한 번도 실행하지 않고 정적 분석만 했다(역공학 원칙 3). 이제부터는 소유자의 정품
사본을 **공식 DOSBox-X에서 관찰용으로 실행할 수 있다**. 정적 분석만으로는 오래 걸리거나 추론으로 남는 사실을 화면·메모리·OPL
출력으로 확정하기 위해서다. 해당 사실은 전투 중 도착하는 아군의 칸, 16색 그림의 팔레트 슬롯, 장면별 곡과 전투 중 곡이다(ROADMAP M3·M5).
원작과 같은 지점의 상태를 준비해 두어 사람이 하는 난이도 비교(ROADMAP H)도 돕는다. 난이도 판단 자체는 사람이 한다. 다음 규칙을 지킨다.

1. **에뮬레이터**: DOSBox-X 공식 릴리스(GitHub `joncampbell123/dosbox-x`)만 쓴다. winget 설치기는 관리자 권한을 요구하므로
   같은 릴리스의 포터블 zip을 `res/dosbox/app`에 풀어 쓴다. 원작 패키지에 들어 있는 `DOSBox.exe`(2010년, 출처 불명)는
   실행하지 않는다.
2. **작업 폴더**: 설치 폴더(`res/hero/GAME`)는 계속 읽기 전용으로 둔다(원칙 2). `.gitignore`된 `res/dosbox/GAME`에 복사해 그
   복사본만 마운트한다. 원작은 세이브(`MSAVE*`·`ESAVE*`)를 그 폴더에 쓴다.
3. **복제 방지는 우회하지 않는다**(원칙 4). 시작할 때 묻는 코드는 소유자가 정품 설명서로 입력한다. 그 판정 코드를 해독해 답을
   구하거나 고치지 않는다. 패키지의 `CRACK.COM`(제3자가 만든 상주 패치)은 실행하지 않는다. 정적으로 확인한 결과
   `HERO.COM`은 `SBOPL2.COM`·`GRPDRV.EXE`·`TFDED.COM`·`OPEN.EXE`·`MAIN.EXE`·`END.EXE`만 부르고 `CRACK.COM`은
   부르지 않는다. 코드를 입력한 뒤의 에뮬레이터 상태 저장은 소유자의 로컬 작업 폴더에만 둔다.
4. **관찰 결과는 로컬에만 둔다**(원칙 6). 캡처·메모리 덤프·OPL 기록·상태 저장은 `res/dosbox` 아래나 스크래치에 둔다.
   문서에는 사실(오프셋·수치·칸 좌표·곡 번호)만 **[관찰]** 표지로 적는다. 원칙 6의 범위 안에서 개별 확인값만 적고
   표로 모으지 않는다. 원작 안의 표에서 온 값은 변환기가 읽는 코드의 서명으로 사용자 파일에서 읽으며, 관찰값을 상수 표로
   코드에 넣지 않는다. 캡처·OPL 기록은 테스트 픽스처로도 커밋하지 않는다.
5. **구현 근거**: 관찰로 정한 값도 가능하면 그 값을 정하는 코드 위치(정적 분석)를 함께 적는다. 관찰만으로 정한 값은 "어떤 상태에서
   몇 번 관찰했는지"를 적는다. 엔진은 관찰을 흉내 내지 않고, 사실을 규칙과 데이터로 구현한다(원칙 5·8).

| 대안 | 장점 | 탈락 사유 |
|---|---|---|
| 지금처럼 정적 분석만 한다 | 원칙이 단순하다 | 도착 칸·팔레트·전투 곡이 계속 추론으로 남거나 해독에 오래 걸린다 |
| 소유자가 원작을 플레이하고 결과를 알려 준다 | 실행 주체가 사람이다 | 사람의 시간이 가장 비싸다. 관찰 환경이 있으면 사람은 체감 확인(난이도·소리)에만 쓰면 된다 |
| 패키지의 DOSBox(2010)를 쓴다 | 이미 있다 | 출처를 확인할 수 없는 바이너리이고 디버거·상태 저장·OPL 기록이 없다 |

**근거**: 정품 소유자가 에뮬레이터로 자기 사본을 돌리는 것은 이 프로젝트가 대체하려는 사용 방식 그대로다. 관찰은 상호운용(원작
파일을 읽는 호환 구현)을 위한 사실 확인에만 쓰고, 복제 방지 우회·원작 바이트 배포는 계속 하지 않는다. 운영 방법은
`docs/reverse-engineering/METHOD.md` 2.8절, 작업 계획은 `docs/ROADMAP.md` M0에 있다.

## D23. 루트마다 다른 원작 출진은 루트별 전투로 만들고 캠프 앞에서 플래그로 고른다 (2026-10-01)

**결정**: 원작은 한 전투의 출진 설정(`battle_setup`: 출진 칸, 승리·패배 조건 무장)과 적·우군 명단(`battle_roster`)을
루트의 플래그로 고른다. 고르는 방법은 두 가지다: `if_flags` 가드로 고르거나, 플래그가 켜져 있어야 서는 손님 칸(`requires_flag`)을
둔다. 변환기는 이 플래그들의 값 조합마다 전투를 다시 읽는다. 그 결과가 서로 다르면 조합마다 전투를 하나씩 만든다.
이름은 `<id>`와 `<id>_f<플래그>…`이고, 처음으로 성립하는 읽기(모두 꺼진 쪽이 성립하면 그것)가 `<id>`를 가진다. 캠페인은 그 전투의 캠프 앞 `Branch`
노드(`<id>_which`)에서 실행 중의 플래그를 보고 변형의 캠프로 간다. 변형은 모두 `<id>`의 이벤트 장면·플래그·outro를 같이
쓴다. 엔진의 데이터 형식은 바뀌지 않는다.

- 어느 플래그로 나누는가: 그 전투의 가드와 손님 칸이 보는 플래그 중 장의 스크립트가 켜는 것만 센다. 이야기가 전투 전에
  값을 정해 두는 플래그는 나누지 않고 그 값으로 읽는다. 예를 들어 사수관 손님의 플래그 0·1은 출진 전 대화가 항상 켠다.
  "정해 둔다"의 기준은 이렇다: 그 플래그를 어떤 전투 블록도 켜지 않고, 이야기 장면이 분기(`@if`·`@choice`·`@goto`·`@label`·
  `@end`) 앞에서만 켜며, 그 전투에 이르는 모든 경로에서 값이 같다(`chapters::army_at_steps`). 한 전투가 볼 수 있는 플래그는
  셋까지만 나누고, 넘으면 모두 꺼진 쪽으로 읽고 기록한다.
- 루트가 전투를 건너뛸 때: 성립하지 않는 읽기(그 루트에서는 이 전투가 없음)는 첫 변형으로 보내고 기록한다. 변형이 변환에
  실패하면 그 루트도 첫 변형으로 간다. 변형은 `<id>`의 장면을 같이 쓰므로, 변형의 장면이나 outro의 소속 이동이 `<id>`와
  다르면 오류로 보고한다.
- 그 루트의 전투인가: 전투에 맞는 설정(적 명단의 무장을 격파 목표로 둔 설정)이 어느 루트에서든 있는 블록 가운데 마지막 블록을
  기준으로 한다. 어떤 루트가 그 블록의 맞는 설정을 모두 건너뛰면, 그 루트에서는 이 전투를 치르지 않는다. 그 루트는 변형을
  만들지 않고 첫 변형으로 간다. 예: 허창 마을은 플래그 89이면 다른 전투(213)를 세운다. 전투 블록 안에서 맵을 읽는 레코드
  뒤에 있는 설정은 다음 전투의 것이다.
- 실물 결과(2026-10-01)

  | 전투 | 갈리는 플래그 | 내용 |
  |---|---|---|
  | 1장 계교 `c1_s0_b15` | 133 | 거록 길의 적군 |
  | 4장 진창 `c4_s1_b2`·장안 `c4_s1_b3` | 38 (방통 사망) | 방통 생존이면 방통, 사망이면 조운이 "퇴각하면 패배" |
  | `c4_s2_b2` | 218 | 장요가 적으로 참전(앞 전투 허창 2의 개막이 켬: 개막의 `run` 단계를 전투 시작 이벤트로 옮겨야 닿음) |

  사수관·호로관은 변형 없이 손님(공손찬·도겸)이 자기 칸의 우군으로 선다.

| 대안 | 장점 | 탈락 사유 |
|---|---|---|
| 유닛에 조건(`when`)을 다는 엔진 형식(ROADMAP 처음 안) | 명단만 다를 때는 전투 하나로 끝난다 | 출진 설정(패배 조건 무장·출진 칸)이 다른 진창·장안에는 결국 전투를 나눠야 해서 두 수단이 생긴다. 공개 형식(MODDING)과 검증 규칙(같은 무장·같은 칸 중복 오류의 예외)이 늘어난다 |
| 지금처럼 한쪽으로 고정 | 단순하다 | 다른 루트에서 원작과 다른 전투가 된다(계교의 적군, 진창·장안의 패배 조건) |
| 플래그를 모두 나눔(이야기가 정하는 것까지) | 판단 규칙이 없다 | 사수관·호로관에 이야기가 결코 닿지 않는 변형이 셋씩 생기고, 이야기가 실제로 닿는 전투가 `<id>`가 아니게 된다 |

**함께 고친 결함 (#84)**: 소속 판단에서 이야기가 한 번도 옮기지 않는 무장은 "군에 있음"이었다. 그래서 합류하지 않는 동맹
무장이 출진 필수가 되었고, 캠프가 이들을 빼면서 출진 칸이 밀렸다(1장 7개 전투와 서장 2개 전투). 이제 그런 무장은 시작
무장이거나 어디선가 합류할 때만 군에 있다고 보고, 나머지는 그 칸의 우군이 된다.

## D24. 군에 없는 무장의 레벨·병종 변경은 합류할 때까지 맡아 둔다 (2026-10-01)

**문제**: 원작은 다른 군에 있는 무장에게도 `add_levels`·`set_class`를 적용하고, 그 무장은 나중에 그 상태로 유비군에 합류한다
(4장 오의 장수들은 합류 전에 레벨이 11 오른다). 엔진의 `@level`·`@class`는 군에 있는 무장에게만 듣고 나머지는 조용히 버렸다.
`growth_after_joining`(`chapters.rs`)은 같은 장면 안에서 `@join` 앞의 변경을 뒤로 옮길 뿐이라, 장면이나 전투를 넘어서는
변경은 사라졌고 그 무장은 원작보다 낮은 레벨로 들어왔다.

**결정**: `CampaignState`에 `pending_growth: BTreeMap<무장 id, Growth { levels, class }>`를 둔다. 팩에 있는 무장이 군에 없을 때의
`@level`은 `levels`에 더하고 `@class`는 `class`에 마지막 것을 적는다. `CampaignState::join`이 무장을 `officers.toml`의 값으로
만든 뒤 쌓인 병종(장비 처리 포함)과 레벨(레벨 상한까지)을 한 번 적용하고 항목을 지운다. 팩에 없는 무장은 전처럼 `NotInArmy`다.
세이브 형식은 이 필드 하나가 늘고, 비어 있으면 쓰지 않으며(`skip_serializing_if`) 없는 세이브는 빈 표로 읽는다. 이 필드를 모르는
이전 릴리스는 세이브의 알 수 없는 필드를 조용히 버리므로, 읽고 다시 저장하면 쌓인 성장이 사라진다. 그래서 필드가 비어 있지 않은 세이브는
새 저장 버전 `GROWTH_SAVE_VERSION`(3)으로 적는다(`SaveGame::stamp_version`, 일반 슬롯 저장도 거친다): 버전 3을 모르는 이전 릴리스는
`TooNew`로 거절한다. 비어 있는 동안의 세이브는 전처럼 버전 1·2이고 이전 릴리스도 읽는다. `leave`로 군에서 나간 무장이 다시 합류하는
규칙(처음 값에서 시작)은 그대로다.

| 대안 | 장점 | 탈락 사유 |
|---|---|---|
| 변환기가 장면을 넘어 `@level`을 `@join` 뒤로 옮김 | 엔진이 바뀌지 않는다 | 합류가 전투 이벤트(`orig_join_*` 플래그)나 다른 장에 있을 수 있어 장면 순서만으로는 못 따라간다. 변환기가 경로를 알아야 한다 |
| 군 밖 무장도 `roster`에 `away`로 넣음 | 상태가 한 곳에 있다 | 군 밖 무장이 로스터·출진 화면·`@leave` 규칙에 섞이고, 아직 합류하지 않은 사람이 "군에 있음"으로 보인다 |

**영향**: `@level`·`@class`의 공개 의미가 군 밖 무장에게 넓어진다(MODDING의 두 항목). 변환기 쪽 변경은 없다. 세이브 호환은 위와 같다(PR #88의 Codex 리뷰가 짚어 버전 3을 더함). 원작 모드에서는 합류하지 않는 무장(도겸 +6 등)의 항목이 지워지지 않으므로 1장 중반부터 세이브가 버전 3이 되어, 이전 릴리스는 그 세이브를 읽지 못한다. 의도한 거절이다(조용히 성장을 잃는 것보다 낫다).
이후(이슈 #90, 2026-10-04): 변환기가 원작 장 어디에서도 군에 합류하지 않는 무장(도겸 등)의 이야기 속 `@level`·`@class`를 쓰지 않는다.
합류하지 않는 무장은 변환 단계에서 알 수 있고(시나리오 전체의 `set_country`/`set_allegiance` 0), 그 성장은 어디에도 쓰이지 않기 때문이다.
그래서 원작 모드 세이브는 실제로 나중에 합류할 무장의 성장이 쌓여 있을 때만 버전 3이 된다. 엔진은 맡아 둔 레벨을 레벨 상한까지만 쌓는다.

## D25. 원작에 없는 기능은 선택형으로 넣는다: 기본값은 원작 그대로 (2026-10-01)

**배경**: 소유자는 원작에 없던 기능을 원한다. 난이도(쉬움·기본·어려움), 무장 능력치 조정, 원작 얼굴 대신 공개된 옛 초상화,
원작에서 아쉬웠던 효과(화면 연출·새 전투 규칙·편의 기능)다. 프로젝트의 본체는 원작 재현(D21)이므로, 이것들이 원작 플레이를
바꾸지 않게 할 규칙이 필요하다.

**결정**

1. **기본값은 원작 그대로다.** 추가 기능은 모두 고를 때만 켜진다. 새 게임의 기본 선택과 설정의 기본값은 지금의 원작 모드와
   숫자 하나 다르지 않다. 골든 테스트와 캠페인 시뮬레이션은 기본값으로 돌아 이것을 지킨다.
2. **한 판의 규칙을 바꾸는 선택은 새 게임에서 정하고 세이브에 둔다.** 난이도, 능력치 자유 조정, 확장 규칙이다
   (`CampaignState::difficulty`·`free_edit`·`extended_rules`, 타이틀 "새 게임"의 설정 메뉴). 게임 도중에는 바꾸지 않는다.
   하나라도 켜진 판(`CampaignState::off_original`)의 세이브는
   - 세이브 목록에 `[어려움·조정·확장]`처럼 표시하고,
   - 세이브 버전 4(`OPTIONS_SAVE_VERSION`)를 찍어 이 기능이 없는 게임이 불러오지 않게 한다(`TooNew`). 그런 게임은 그 판을
     원작 수치로 조용히 이어 가게 되기 때문이다. 기본 판의 세이브는 지금처럼 내용에 맞는 가장 낮은 버전(1·2·3)이다.
   - v0.4.1부터 버전 2 이상의 세이브는 그 버전이 필요한 이유를 글로 함께 적는다(JSON `needs`, `save::version_needs`).
     거절하는 쪽은 새 버전의 이유를 알 수 없으므로 세이브가 들고 다닌다. 0.4.1 이후의 게임은 더 새 세이브를 거절할 때
     목록에 그 이유를 보이고("새 버전의 기록입니다: …", 30자까지), 필드를 모르는 0.4.0 이하는 무시하고 예전 문구를 낸다.
     새 저장 버전을 만들 때는 `version_needs`에 이유를 더한다(테스트가 빠뜨림을 잡는다). 그 목록에 갈 수 있도록 타이틀의
     "불러오기"는 읽을 수 없는 기록만 있어도 켜진다(`saves::any_record`; "이어하기"는 읽을 수 있는 기록이 있어야 한다).
3. **보기만 바꾸는 선택은 설정(`settings.json`)에 둔다.** 초상화 종류, 화면 연출, 편의 기능은 판과 상관없이 언제든 켜고 끈다.
   설정 화면의 "얼굴(원작/공개 초상화)", "위험 범위(끔/켬)", "전투 연출(원작/강화)"이다(PR #91). 예전 `settings.json`은 새 항목을
   기본값으로 읽는다. 피해 숫자는 이미 떠 있었으므로 "강화"는 빨간 `-N`과 큰 타격의 지도 흔들림만 더한다.
4. **난이도는 적의 레벨만 옮긴다.** 쉬움 −2, 기본 0, 어려움 +2. 전투를 세울 때 `side = "enemy"` 유닛(이름 있는 무장과 일반
   유닛, 증원 포함)의 레벨에 더한다. 결과는 1 이상이고, 어려움은 `level_cap`을 넘기지 않는다. 팩이 상한보다 높게 둔 레벨은
   상한으로 깎지 않는다(쉬움은 그대로 2를 뺀다). 아군·우군과 손님은 바뀌지 않는다. HP·MP·공격·방어·배우는 책략은 원작 공식대로
   레벨을 따른다(RULES.md §2·§7). 그 결과로 경험치도 바뀐다. 경험치는 레벨 차로 정해지므로 어려움에서는 한 번에 더 많이,
   쉬움에서는 덜 받는다. 이것은 의도한 효과로 둔다. 값은 엔진 상수(`Difficulty::enemy_level_offset`)이고, 사람이 해 본 뒤 조정한다.
5. **능력치 자유 조정은 무장 정보의 상세 화면에서 한다.** 무력·지력·통솔을 1–100(금단의 비법과 같은 상한)에서 1씩 고친다(길게 누르면 1초 뒤 5씩, 2초 뒤 10씩: BACKLOG의 PR #89 리뷰).
   군에 있는 무장만 고칠 수 있다(`CampaignState::set_ability`). 레벨·병종·장비는 범위 밖이다. 캠프 메뉴는 이미 10항목이라
   새 항목을 더하지 않는다.
6. **확장 규칙은 협공 하나로 시작한다.** 공격받는 유닛과 상하좌우로 붙은 공격자 편 유닛(플레이어와 우군은 한 편, 공격자 자신
   제외) 1명당 그 공격의 피해가 10 % 늘고 최대 30 %다(RULES.md §4). 양 진영이 똑같이 받는다. 반격에는 붙지 않는다. 공격자가 어디서
   치는지는 보지 않으므로, 이동 전에 낸 예보와 AI의 공격 평가가 실제 피해와 같다. 예보 창은 `협공 +20%`처럼 보여 준다.
   AI의 위험 추정(적이 다음 턴에 줄 피해)은 다른 유닛이 어디에 설지 몰라 최대치(+30 %)로 잡는다. 그래서 군주가 "안전한
   칸"으로 고른 곳은 협공을 받아도 안전하다(2차 리뷰).

| 대안 | 장점 | 탈락 사유 |
|---|---|---|
| 적 능력치(무력·지력·통솔) 배율 | 레벨이 같아 경험치가 그대로다 | 소유자가 레벨 방식을 골랐다. 능력치 항은 `4000 / (140 - x)`라 배율의 체감이 무장마다 크게 달라진다 |
| 경험치·금 배율 | 성장 속도로 조절한다 | 소유자가 고르지 않았다. 전투 자체의 어려움은 그대로다 |
| 팩 데이터(`rules/game.toml`)에 난이도 표 | 모드가 값을 바꿀 수 있다 | 원작 모드의 `game.toml`은 변환기가 쓰므로 엔진 기본값이 어차피 필요하다. 모드가 바꾸고 싶다는 요구가 생기면 그때 형식을 연다 |
| 난이도를 설정(`settings.json`)에 둠 | 언제든 바꾼다 | 판 도중에 바뀌면 세이브가 어떤 조건에서 진행됐는지 알 수 없다 |
| 세이브 버전을 그대로 둠 | 옛 게임도 모든 세이브를 읽는다 | 옛 게임이 선택이 켜진 판을 원작 수치로 조용히 이어 간다 |
| 캠프 메뉴에 "능력치 조정" 항목 | 찾기 쉽다 | 원작 화면 틀(640×400)의 캠프 메뉴가 10항목이라 넘칠 수 있다(ROADMAP M7-1과 같은 문제) |
| 확장 규칙으로 배후 공격(방향) | 방향이 의미를 가진다 | 공격자가 어디서 치는지에 따라 달라져 이동 전 예보·AI 평가와 어긋난다. 원작의 방향은 그림일 뿐이다 |
| 확장 규칙으로 독·마비 같은 상태이상 | 책략이 다양해진다 | 원작 데이터에 그런 책략이 없어 새 책략·AI·회복 수단까지 만들어야 한다. 협공 뒤에 요청이 있으면 본다 |

**남은 일**: 순서와 방법은 [ROADMAP.md](ROADMAP.md)의 X 단계에 둔다. 공개 초상화 토글(X2), 편의 기능(X4)과 화면 연출(X5)은
설정형 묶음으로 따로 간다.
