# 원작 파일 형식 명세 (한국어 DOS/V판 기준)

> **English summary** — Consolidated file-format specification of KOEI's 1995 *Sangokushi Eiketsuden*
> (DOS/V family), as reverse-engineered by static analysis of one owned Korean DOS/V copy. It covers edition
> identification (`DISK*.R3I` + text statistics), the `LS11`/`Ls11` archive (byte order chosen by the magic's
> spelling, dictionary + variable-length-code LZ codec), 6-byte-table containers with data-relative offsets,
> the TF-DCE image codec of `TFDED.COM` (portraits and screens), the 9-slot `[B][R][G]` palette bank inside
> `MAIN.EXE` (slot chosen at run time from data), 16×16 4-plane cells and the sprite archives, packed planar
> images, battle maps (`[W][H][chips][terrain per 2×2]`, chip bank = `HEXZCHP` 0 + 1 or 2 chosen by a list in
> `MAIN.EXE`), battle-scene strips, campaign/town/palace maps, 20 terrain codes, message files (16-bit section
> bases restored past 64 KiB; dialogues `[u16 speaker][text]00 … FFFF` vs plain strings, delimited only by
> the bytecode), the scenario bytecode (scenes → blocks → 10-byte trigger records → scripts, opcodes
> `0x00`–`0x3D` with operand lengths), `IPPAN0` and `BAKDATA` tables, and how every `MAIN.EXE` table is
> located at run time through the code that reads it. Every item carries a confidence mark. KOEI's data
> values (colours, stats, text, name lists) are deliberately not reproduced; the document says how to read
> them instead.

이 문서는 사실(오프셋·구조·알고리즘)만 적습니다. 원작의 **데이터 값**(팔레트 색, 능력치 표, 대사, 이름
목록 전체, 규칙 표의 바이트)은 옮기지 않고, 그것을 **어떻게 읽는지**만 적습니다. 코드의 의미를 이해하는 데
꼭 필요한 짧은 명칭(지형 코드·소속·병종의 뜻)과 공개 공략으로 이미 알려진 확인용 수치만 예외로 둡니다.
원칙과 문서 구성은 [README.md](README.md), 분석 방법은 [METHOD.md](METHOD.md), 남은 과제는
[STATUS.md](STATUS.md)에 있습니다.

## 1. 표기 규칙

**신뢰도 표기** — 항목마다 붙입니다.

| 표기 | 뜻 |
|---|---|
| **[검증]** | 실물 파일 전체에 대해 구조 불변식이 성립하고(모든 바이트가 설명되거나 입력을 정확히 소비), 결과를 눈이나 공개 수치로 확인함 |
| **[코드]** | `MAIN.EXE` 등 실행 파일의 읽는 코드를 정적으로 읽어 확인함(데이터로도 모순 없음) |
| **[관찰]** | 원작을 공식 DOSBox-X에서 실행해 화면·메모리·OPL 출력으로 확인함(DECISIONS D22). 관찰한 상태와 횟수를 함께 적음 |
| **[추론]** | 데이터와 모순은 없지만 코드나 공개 자료로 확정하지 못함 |
| **[미상]** | 모름. 추측해서 쓰지 않음 |
| **[외부]** | 다른 사람의 공개 조사에 나온 주장이며 우리가 실물로 확인하지 않음 |

**오프셋 표기**

* **파일 오프셋**: 파일 첫 바이트 기준.
* **이미지 오프셋**(`MAIN.EXE`): 파일 오프셋 − MZ 헤더 크기. 역어셈블러가 로드 이미지 기준으로 보여 주는 주소입니다.
* **DS 오프셋**: 데이터 세그먼트(DGROUP) 기준. 파일 오프셋 = MZ 헤더 크기 + DGROUP × 16 + DS 오프셋(15절).
* 괄호 안의 "한국어판 …" 값은 **검증한 사본 하나**의 위치입니다. 다른 빌드에서는 달라질 수 있으므로 구현은
  고정 오프셋 대신 서명(15절)으로 찾습니다.
* 따로 적지 않으면 다바이트 정수는 **리틀엔디언**(`u16le`, `u32le`)입니다. LS11 디렉터리만 예외입니다(4절).
* `W×H`는 가로×세로, 격자는 따로 적지 않으면 **행 우선**(한 줄씩 왼쪽→오른쪽, 위→아래)입니다.

## 3. 판본 식별

코드: `crates/hero-import/src/edition.rs`, `diskimage.rs`. 지정한 폴더 **바로 아래** 파일만 봅니다.

| 판본 | 판정 규칙 | 신뢰도 |
|---|---|---|
| Steam 2017 | `Eiketsuden1_Launcher.exe`가 있음 | 높음(내용 형식은 미상) |
| 한국어 DOS/V | `DISK1.R3I`에 일본어 DOS/V 헤더 + `MAIN.EXE`·`SNR0M.R3` + 텍스트가 한국어 | 높음 **[검증]** |
| 한국어 DOS/V (대체 규칙) | `DISK1.R3I`에 EUC-KR `DOS/V 삼국지영걸전` | 높음 **[외부]**(실물에서 못 봄) |
| 번체 중문 DOS | DOS/V 파일군 + 텍스트가 뚜렷한 Big5 | 중간 **[추론]**(합성 데이터만) |
| PC-98 디스크 이미지 | D88 / Anex86 FDI·HDI 헤더 | 높음(이미지 안 파일은 안 읽음) |
| 그 밖 | — | `unknown`(추측하지 않음) |

* **`DISK*.R3I`** **[검증]**: 각 107바이트. 한국어판도 **일본어 DOS/V판 헤더를 그대로** 갖습니다 — Shift-JIS로
  `DOS/V 三國志英傑伝 ﾃﾞｨｽｸn Ver 1.00 Rel 1.00`, `(C)(P) 1995 KOEI CO.,LTD`, `MADE IN JAPAN`, 끝에 `0x1A`.
  그래서 헤더는 "DOS/V 계열"만 알려 주고, 언어는 텍스트로 정합니다.
* **한국어 판정** **[검증]**: `SNR0M`–`SNR4M`, `IPPAN0M`, `BAKDATA`(LS11이면 모든 항목을 풀어서)의 2바이트 쌍을
  셉니다. 선행 바이트 ≥ 0x81(0xFF 제외)이면 쌍 하나. EUC-KR 한글 영역은 선행 0xB0–0xC8, 후행 0xA1–0xFE.
  **한글 쌍 ≥ 500이고 전체 쌍의 80 % 이상이 한글 영역**이면 한국어입니다. 검증 사본: 137,114쌍 중 134,374쌍(98 %)이
  한글 영역, Big5 전용 쌍 9개.
* **EUC-KR/Big5 구분** **[검증: EUC-KR 쪽]**: Big5만 쓰는 후행 바이트 0x40–0x7E를 세어, 그런 쌍이 전체의 1/6
  이상이면 Big5, 1/50 이하이면 EUC-KR, 그 사이는 결론 없음.
* 일본어 헤더에 한국어가 아닌 텍스트(일본어 DOS/V판으로 보이는 것)는 `unknown`입니다(실물을 본 적 없음).
* **D88** **[추론]**: 0x2B0 바이트 헤더, 0x1A 쓰기 금지(0x00/0x10), 0x1B 매체 종류, 0x1C `u32le` 전체 크기 = 파일
  크기, 0x20부터 트랙 오프셋 표. **FDI/HDI**: `u32le` 8개(0, 종류, 헤더 크기, 데이터 크기, 섹터 크기, 트랙당
  섹터, 헤드, 실린더)이고 헤더 + 데이터 = 파일 크기, 섹터 × 트랙당 섹터 × 헤드 × 실린더 = 데이터 크기.
  둘 다 크기 일관성 검사라 우연히 맞을 확률이 매우 낮습니다.

## 4. LS11 / Ls11 아카이브

코드: `ls11.rs`. `.R3` 파일 대부분의 컨테이너입니다. 같은 컨테이너가 다른 KOEI 게임(조조전 `.e5`의
`Ls10/Ls11/Ls12`, 대항해시대 II)에도 쓰였다는 공개 자료가 있습니다 **[외부]**.

### 4.1 배치 **[검증]**

```text
0x000  16 B     매직 4바이트("LS11" 또는 "Ls11") + 0 12바이트
0x010  256 B    바이트 사전(파일의 모든 항목이 공유)
0x110  N × 12 B 디렉터리: [저장 길이][복원 길이][절대 파일 오프셋], 각 u32
       …        0 종결자(실물은 4바이트, 구현은 15바이트까지 허용)
데이터          항목 i는 offset[i]에서 시작, offset[i+1] = offset[i] + 저장 길이[i],
                마지막 항목은 파일 끝에서 정확히 끝남
```

* **바이트 순서** **[검증]**: 매직 철자가 정합니다. `LS11`(대문자 S) = 디렉터리 **빅엔디언**, `Ls11`(소문자 s) =
  **리틀엔디언**. 한국어판은 21개가 `LS11`, `OPGRP`·`END1GRP`·`END2GRP`(오프닝·엔딩, `OPEN.EXE`/`END.EXE`가 읽음)가
  `Ls11`입니다. 사전·디렉터리 위치·체인 규칙·코덱은 같습니다.
* **디렉터리 끝**: 첫 항목의 오프셋이 데이터 시작이며, 디렉터리를 읽다가 그 위치에 닿거나 전부 0인 항목을 만나면
  끝납니다. 데이터 시작 = 0x110 + 12N + 4 (예: 181개 항목인 `HEXBCHR.R3`는 0x990 — 골든 테스트 확인값).
* `Ls10`/`Ls12`/`LS10`/`LS12` 매직은 같은 계열의 다른 코덱으로 알려져 있어 "지원 안 함"으로 보고합니다(실물에는 없음).

### 4.2 코덱 **[검증]**

* 저장 길이 = 복원 길이이면 **원시 저장**입니다.
* 그 밖에는 **MSB 먼저** 읽는 비트 스트림입니다. 가변 길이 정수 하나는 `k`비트 접두(1이 `k−1`개 뒤에 0 하나 —
  이진수로 `2^k − 2`) 뒤에 `k`비트 값이 붙고, 둘을 더합니다. 즉 `k = 1`은 0–1, `k = 2`는 2–5, `k = 3`은 6–13 …
* 값 `v < 256`: 리터럴 `사전[v]`. 값 `v ≥ 256`: 출력에서 `v − 256`바이트 앞부터, 길이 = (다음 정수) + 3만큼
  복사(겹침 허용).
* 끝: 정확히 복원 길이만큼 나오고, 마지막 바이트의 채움 비트 말고는 입력이 남지 않아야 합니다.
* 관찰값: 역참조 거리 최대 8,188(8 KiB 창으로 보임), 길이 최대 512. 디코더는 이 값을 강제하지 않습니다 **[추론]**.
* 사전은 빈도순 순열로 보입니다. 우리 인코더(`ls11::build`)는 빈도순 사전을 만들어 테스트 픽스처를 씁니다.

### 4.3 불변식과 알려진 손상

검사: 매직 뒤 0 12바이트, 디렉터리 체인, 항목이 파일 안에 있음, 마지막 항목 = 파일 끝, 정확한 복원 길이, 입력 완전
소비. 한국어판 24개 아카이브 중 **23개가 모든 항목에서 통과**합니다.

**`OPGRP.R3` 손상** **[검증: 이 사본의 상태]**: 검증한 사본(SHA-256 `eed970e7…6f2b`)은 파일이 디렉터리 합계보다
6바이트 깁니다(0xB40AA vs 0xB40B0). 0–26번 항목은 정확히 복원되고, 27번은 그림 앞부분 약 110줄만 정상입니다.
28번 이후 압축 항목은 처음 몇 바이트에서 실패하고, 원시 항목은 `NPK016` 헤더 대신 잡음입니다. 파일 오프셋 약
0x60400(1 KiB 경계)부터 12바이트 반복 문자열 수가 64 KiB당 0–117개에서 2만 개 이상으로 뛰어, 그 뒤가 다른 데이터로
덮인 것으로 봅니다. 1비트 반전·1–6바이트 삭제로는 복구되지 않았고 다른 사본으로 교차 확인하지 못했습니다.
골든 테스트는 이 파일을 해시·정확한 오류 문자열·정상 항목 수(27)로 `KNOWN_DAMAGED`에 기록합니다.

## 5. 6바이트 테이블 컨테이너

코드: `table6.rs`. `FACEDAT.R3`, `PACKGRP.R3` **[검증]**.

```text
0      N × 6 B   [u32le 오프셋][u16le 길이]
N×6    데이터    오프셋은 데이터 영역(테이블 끝) 기준: offset[0] = 0,
                 offset[i+1] = offset[i] + 길이[i], 마지막 항목은 파일 끝에서 끝남
```

* **N은 파일에 없습니다.** `MAIN.EXE`의 `FACEDAT` 로더(이미지 오프셋 0x1203C)는 테이블 크기 0x5A0(= 240 × 6)을 코드에
  박아 두고 `항목 번호 × 6`에서 오프셋·길이를 읽은 뒤 `0x5A0 + 오프셋`으로 이동합니다 **[코드]**.
* 파일만으로는 `N × 6 + Σ길이[0..N] = 파일 길이`를 만족하는 `N`을 찾습니다. 좌변은 `N`에 대해 순증가하므로
  답은 많아야 하나입니다.
* 한국어판: `FACEDAT` 240개(데이터 0x5A0부터), `PACKGRP` 38개(데이터 0xE4부터). 예: `FACEDAT` 항목 1의 오프셋은 0x516.
* **정정**: 조사 노트는 오프셋을 파일 기준 절대값으로 적었지만 실물은 데이터 영역 기준 상대값입니다.

## 6. TF-DCE 이미지 압축

코드: `tfdce.rs`. `TFDED.COM`("DOS/V Series TF-graphic Data Expand Driver", 형식 서명 `TF-DCE 5.11 1994`, 1,985바이트
상주 드라이버)을 정적으로 역어셈블해 확인했습니다 **[검증]**(다른 구현은 참고하지 않음).

### 6.1 호출 규약 **[코드]**

* `MAIN.EXE`에는 `int 62h`가 한 곳뿐입니다: 래퍼(이미지 0x6B2C) ← 도우미(이미지 0xCF50) ← 유일한 호출자(이미지 0x12224).
* 매개변수 블록: `[x/8, y, 데이터 세그먼트, 데이터 오프셋, 플래그, 모드]`. 게임은 플래그 1(네 번째 플레인 처리),
  모드 0(해제)으로 부릅니다. 모드 0·1 = 해제, 모드 2 = 16바이트 서명 `TF-DCE 5.11 1994` 비교(게임 데이터에는 안 쓰임).
* 드라이버는 VGA 메모리에 플레인별로 직접 씁니다. 한 줄 80바이트, 목적지 = `y × 80 + x + 0xC80`(화면 y + 40줄).
  우리 디코더는 같은 결과를 일반 버퍼에 만듭니다.

### 6.2 헤더

| 바이트 | 뜻 |
|---|---|
| `u8 L` | 헤더 길이. 뒤의 `L−1`바이트는 건너뜀(알려진 파일은 모두 `02 'T'`) |
| `u8 W` | 가로 바이트 수(8 px 단위) |
| `u16le H` | 줄 수 |
| `u16le` | 플레인 방식: 처리하는 플레인마다 니블 하나, 낮은 니블부터 |
| `u8` | 플레인 순서: 2비트 플레인 번호 4개, 낮은 비트부터 = 처리 순서. 실물: `C6 C9 D2 D8 E1 E4`, 플레인 3은 항상 마지막 |
| `u8` | 플래그: `0x40` = 32바이트 블록이 뒤따름(팔레트로 보이나 드라이버가 두 분기 모두에서 건너뜀), `0x20` = 사전(`u8 개수` + `개수 × u16le`). 비트 7은 무시. 실물은 모두 `0x20` |
| … | 방식 3을 쓰는 플레인들의 명령 스트림이 차례로 |

### 6.3 플레인 방식

| 방식 | 동작 |
|---|---|
| 0 | 플레인 3(플래그 비트 0 켜짐)이면 0으로 지움, 다른 플레인이면 손대지 않음(우리 디코더는 오류 — 실물에 없음) |
| 1 | 다음 바이트로 플레인 전체를 채움 |
| 2 | 다음 바이트가 가리키는 **순서 위치**의 플레인을 복사(값이 3보다 크면 드라이버는 4칸 표 밖을 읽음 — 실물에 없음; 구현은 `& 3`) |
| 3 | 명령 스트림 |
| 4 | 손대지 않음(오류로 처리) · 5 이상 무효 |

실물에서 본 방식 워드: `0x0333`, `0x3333`, `0x0223`.

### 6.4 명령 스트림

한 플레인(`W` 바이트 열 × `H` 줄)을 **열 단위 뱀 순서**로 한 바이트씩 씁니다: 0열 위→아래, 1열 아래→위, … 마지막
바이트를 쓰는 순간 그 플레인의 스트림이 끝나고, 진행 중이던 명령은 버려집니다. 리터럴은 쓰는 만큼만 읽습니다.
`n` = 명령의 낮은 니블, `b` = 다음 바이트.

| 명령 | 동작 |
|---|---|
| `00`–`1F` | 사전 단어 `d = dict[cmd]`: 명령 `d & 0xFF`를 실행하되 바이트 인자는 스트림 대신 `d >> 8` |
| `2n b` | 뱀 순서로 `b`칸 앞에서 `n+3`바이트 복사(겹침 허용) |
| `3n b` | 순서 위치 `n>>2` 플레인의 같은 자리에서 `b+2`바이트, `n&3`에 따라 0 그대로·1 NOT·2 오른쪽 1비트 회전·3 왼쪽 1비트 회전 |
| `4n b` | 같은 줄 `n+1`바이트 열 왼쪽에서 `b+2`바이트 복사(원본도 함께 이동) |
| `5n` / `9n` | 다른 플레인 같은 자리 값 AND 마스크(6.5) |
| `6n b1 b2` | 쌍 `b1 b2`를 `n+1`번 |
| `7n` | 리터럴 `n+1`바이트 |
| `8n b` | `b`의 낮은 니블 `L`·높은 니블 `H`로 쌍 `(L×0x11, H×0x11)`을 `n+1`번 |
| `A0`–`FF b` | `b`를 `cmd − 0x9E`번(2–97) |

### 6.5 마스크와 사전 단어

* 최근 마스크 4개를 두고 이미지마다 `00 FF 55 AA`로 초기화합니다.
* `n>>2 < 3`: 원본 = 순서 위치 `n>>2`, 마스크 = 최근 `n&3`번, 쓴 뒤 그 마스크가 바로 앞 칸과 자리를 바꿈(한 칸 앞으로).
  개수 = `b+2`.
* `n>>2 = 3`: 원본 = 순서 위치 `n&3`, 다음 바이트가 새 마스크로 2번 칸에 들어가고(기존 2번은 3번으로), 그다음이 개수 바이트.
* `9n`은 바이트마다 마스크를 왼쪽 회전합니다(`55`/`AA`는 1비트, 그 밖은 2비트 — 디더). `5n`은 회전하지 않습니다.
* **사전 단어**는 낮은 바이트의 높은 니블로 분기합니다: `2` 선형 복사(인자 = 거리), `3` 플레인 변환(인자 = 개수),
  `4` 열 복사(인자 = 길이), `5`/`9` 마스크 복사(인자 = 개수; 선택자 3은 새 마스크 없이 순서 위치 3), `7` 리터럴
  1바이트(인자), `8` 니블 쌍, `A`–`F` 인자로 채우기, `0`·`1`·`6` 아무것도 안 함.

### 6.6 출력과 실물 데이터

* 출력은 **플레인 우선 4bpp**(플레인 p = 색 번호 비트 p, 한 줄 `W`바이트)이며 8절의 `planar::decode`로 읽습니다.
* 검사: 입력 완전 소비, 아직 쓰이지 않은 플레인 읽기 금지, 플레인 밖을 가리키는 역참조 금지, 거리 0 금지.
  한국어판 278개 이미지 모두 위반 없음.
* **`FACEDAT`** **[검증]**: 240개 모두 8바이트 × 80줄 = **64×80 px**(2,560바이트), 색 0–7만 씀(플레인 3은 항상 0).
  색 0–7은 팔레트 슬롯 4를 뺀 모든 슬롯에서 같으므로 얼굴은 슬롯 선택의 영향을 받지 않습니다(7절). 얼굴 번호 ↔
  무장은 `BAKDATA`의 얼굴 필드가 정합니다(14절).

  35 = 208×24 "KOEI PRESENTS", 36 = 272×40 저작권 문구, 37 = 176×112 대리석 무늬. 1·2·37번은 16색을 쓰며 어느
  슬롯이 맞는지는 **[미상]**(슬롯 0–3·5–7이 모두 그럴듯하고 4는 확실히 틀림). 1번(전투 화면 틀)은 전투 맵과 함께 화면에
  있으므로 맵의 팔레트로 그려진다고 보고(**[추론]**), 원작 모드는 맵과 같은 슬롯으로 씁니다. 로더는 이미지 0x1215E(`0xcf5:0x520E`,

  **[검증: 픽셀]**. 원작에서 버튼이 여는 창(기능 메뉴·아군/적군 목록)의 내용은 엔진의 전투 메뉴·부대 일람으로 옮기며, 그림

## 7. 팔레트

코드: `palette.rs`. 팔레트는 데이터 파일이 아니라 **`MAIN.EXE` 안**에 있습니다.

### 7.1 뱅크 **[검증]**

* **9 슬롯 × 48바이트**(16색 × 3바이트), 바로 뒤에 `80 40 20 10 08 04 02 01`. 한국어판: 파일 0x38DF0 = DS 0x1050.
* 한 색 = `[B][R][G]`, 채널마다 하위 4비트만 씀. VGA DAC 6비트로 `(n << 2) | (n >> 2)` 확장.
* **찾는 서명**: 432바이트가 모두 ≤ 0x0F이고, 슬롯 5와 슬롯 8이 같고, 바로 뒤가 `80 40 20 10`인 위치. 후보가 둘
  이상이면 모호함 오류. 고정 오프셋은 쓰지 않습니다.
* 색 순서 근거: 슬롯 4는 모든 채널이 0 또는 15인 8색 디지털 팔레트를 두 번 반복하며 1 = 파랑, 2 = 빨강, 4 = 초록(PC-98
  순서)입니다. 이 순서로 그린 유닛의 피부·머리·칼날이 자연스럽고 GRB·RGB·BGR로는 얼굴이 초록·보라가 됩니다.
* 색 0–7은 슬롯 0–3·5–8에서 같고(윤곽·UI·유닛), 8–15가 슬롯마다 달라 지형 색을 바꿉니다.

### 7.2 슬롯 선택 **[코드]**

* 팔레트 설정 루틴(이미지 0x118CE)은 슬롯 `n`을 DS `0x1050 + 48n`에서 복사합니다.
* 호출부는 상수(슬롯 4)이거나, 게임 상태 구조체(한국어판 DS 0x7A6C)의 +5 바이트 하위 4비트입니다. 그 바이트는 데이터
  레코드의 +8 바이트에서 옵니다. 즉 **어느 화면이 어느 슬롯을 쓰는지는 실행 중 데이터가 정합니다.** 어떤 레코드인지는
  **[미상]**(시나리오·맵 레코드 추적 과제, [STATUS.md](STATUS.md)).

### 7.3 눈으로 본 슬롯 성격과 추출기 기본값 **[추론]**

| 슬롯 | 성격 | 잘 맞는 그림 |
|---|---|---|
| 0 | 도시 | `SMAPBGPL` 0번(도시 야외) |
| 1 | 초록 들판 | 전투 칩·전투 장면·캠페인 맵·유닛 |
| 2 | 건조·가을 갈색 | `SMAPBGPL` 1번(궁궐 실내) |
| 3 | 밝은 초록 | — |
| 4 | 디지털 8색(상수로 설정) | — |
| 5–8 | 갈색 계열(5 = 8) | — |

추출기: 스프라이트·칩·전투 맵·전투 장면·캠페인 맵 = 1, 도시 = 0, 궁궐(`SMAPBGPL` 1번, `PMAP`) = 2, 얼굴 = 0.
PNG는 인덱스 색이라 나중에 슬롯을 바꿔 칠할 수 있습니다.

### 7.4 12비트 팔레트 (`NPK016`)

`NPK016` 헤더 안의 16색 팔레트는 `u16` 하나에 `0x0GRB`(채널당 4비트)입니다 **[추론]**(9절).

### 7.5 `OPEN.EXE` / `END.EXE` 장면 팔레트 **[미상]**

아카이브 이름 문자열 바로 뒤에 4비트 값 블록이 있습니다: `OPEN.EXE` 0xC0C6부터 28 × 48 + 2바이트, `END.EXE` 0xD656부터
43 × 48 + 2바이트(**정정**: 노트는 16 × 48). 슬롯 경계와 어느 그림에 쓰이는지는 오프닝 그림을 풀기 전에는 확인할
수 없어 추출하지 않습니다.

## 8. 평면(planar) 그래픽과 스프라이트 아카이브

코드: `planar.rs`, `sprites.rs`, `image.rs`.

### 8.1 픽셀 배치 **[검증]**

* **플레인 이미지**: 너비 `w`(8의 배수) × 높이 `h`를 플레인 4장이 차례로 저장. 플레인마다 `h`줄 × `w/8`바이트,
  **MSB = 왼쪽 픽셀**, 플레인 p = 색 번호 비트 p.
* **셀**: 16×16 px = 4 플레인 × 32바이트(플레인마다 16줄 × 2바이트) = 128바이트. 여러 셀로 된 그림은 셀을 **행 우선**으로 배치.
* **packed planar**: 8픽셀마다 4바이트(플레인 0, 1, 2, 3 순)가 이어지고, 그 묶음이 왼쪽→오른쪽, 줄이 위→아래.
  `HEXGRP` 0번과 `OPGRP`/`END*GRP`의 원시 그림이 이 형식입니다.
* **투명**: 색 0(모든 플레인 0)이 투명입니다. 엔진은 블릿 마스크를 "플레인 OR의 NOT"으로 만듭니다 **[외부]**(노트).
  얼굴은 불투명으로 씁니다.
* **좌우 반전**: 한 방향만 저장됩니다. 엔진이 불러올 때 바이트 비트 뒤집기·16비트 워드 안 바이트 교환·셀 재배치로
  반대 방향을 만든다고 알려져 있습니다 **[외부]**. 추출기는 저장된 방향만 내보냅니다.

  계산(이미지 0x29789)은 `DS 0x400E + 이동 종류 × 20 + 지형` 값이 255가 아니면 부호 없이 더해 이동력과 비교합니다.
  값은 사용자의 파일에서만 읽고 여기에 옮기지 않습니다. 변환기는 두 표를 읽는 코드(`8A 8F <이동 종류> 2A ED 6B F9 14 8B D8
  80 B9 <비용> FF`, 이미지 0x258B4)와 지형 창의 효과 줄(`… 80 BF <효과> FF 74 10 2A E4 8A 87 <효과> 8D 5E F0`, 이미지
  0x23DD4)로 찾아(`maps::find_move_rules`) 원작 모드의 `rules/terrain.toml`을 씁니다. 지형 효과는 방어(피해 감소 %)로 읽습니다.
* **병종 규칙 표 [코드]**: 병종 19개의 바이트 표 네 개입니다. 공격 계수(DS 0x0FFE)와 방어 계수(DS 0x1012, 20바이트
  뒤)는 공격력·방어력 계산(이미지 0x13A3E·0x13B6C)이 `(레벨 + 10) × (사기 + 4000 / (140 − 무력 또는 통솔) + 계수 × 2) / 10`으로
  씁니다. 엔진의 `(level + 10) * (morale + s(x) + class.atk * 10) / 10`(RULES §2)과 같은 식이라 계수 = `atk × 5`입니다.
  이동력(DS 0x3F8E)과 공격 범위 코드(DS 0x3FE6: 0 상하좌우, 1 주위 8칸, 2 궁병, 3 연노, 4 투석, 255 없음)가 뒤따릅니다.
  변환기는 각 표를 읽는 코드(`9A <먼 호출> 8A D8 2A FF 8A 87 <표>` 뒤에 계수 둘은 `2A E4 2B D2`, 이동력은 `88 46 F9`,
  범위는 `88 46 FE 88`)로 찾아(`maps::find_class_rules`) 원작 모드의 `rules/classes.toml`을 씁니다.
  최대 병력은 `(10 × 표[병종] + 성장[병종] × (레벨 − 1)) × 10`(이미지 0x14308, 병력 표 DS 0x1338, 성장 표 DS 0x134C,
  서명 `B0 0A 8A 5C 20 2A FF F6 A7 <병력> 8B C8 8A 87 <성장> 2A E4 8A 5C 21 4B F7 E3`)이라 엔진 `hp` = 100 × 표,
  `hp_growth` = 10 × 성장입니다(RULES §2).
* **범위를 칸으로 펼치는 함수 [코드]**(이미지 0x28B78): 단계 n과 "책략" 비트(0x80, n을 1 올리고 상하좌우 네 칸을 늘
  넣음)를 받습니다. n ≤ 1(또는 책략)이면 상하좌우, n ≥ 1이면 대각(DS 0x4CFC), n = 2면 직선 2칸(DS 0x4D0C × 2), n ≥ 3이면
  (dx −1..1, dy ±2)와 (dx ±2, dy −1..1), n = 4면 직선 3칸과 대각 2칸을 더합니다. 그래서 병종 범위 코드 0–4 =
  `adjacent4`·`adjacent8`·`archer`·`crossbow`·`catapult`, 책략 도달 코드 0–3 = `range8`·`range12`·`range20`·`range28`
  (5×5 전체 + 직선 3칸)입니다(엔진 `RangeSpec`). 중심 칸은 플래그 비트 0이 있을 때만 넣는데 책략 명령은 0으로 부르므로
  원작의 도달에는 시전자 칸이 없습니다. 엔진의 `range8` 등은 시전자 칸을 포함하고, 원작에서 자기 자신을 대상으로 할 수
  있는지(다른 경로)는 **[미상]**입니다.
* **책략 표 [코드]**: 책략 36개의 이름 포인터(DS 0x4438, 먼 포인터), 도달 코드(DS 0x44C8), MP(DS 0x44EC), 습득 레벨
  행렬(DS 0x4510, 책략마다 병종 19개 바이트, 255 = 배우지 않음)입니다. 책략 명령이 도달 코드와 MP를 확인하는 코드(`8A 87
  <도달> 88 46 F9 8A 44 0D 38 87 <MP> 76`, 이미지 0x27E73)와 책략 목록이 습득 레벨을 비교하는 코드(`6B D9 13 8A 4E FD 03
  D9 38 87 <행렬> 77`, 이미지 0x2729F: 유닛 레벨 ≥ 값이면 앎)로 찾습니다(`maps::find_strategy_rules`). 책략 순서는
  `pack::STRATEGY_IDS`(기본 팩 id)로 옮기고, 원작 모드의 `rules/strategies.toml`(MP·도달)과 `rules/classes.toml`의 병종별
  습득 목록을 씁니다.
* **책략 효과 [코드]**(책략 명령 이미지 0x27E30–0x2841E, 피해 계산 0x2AA74, 회복 0x28420, 大 지원 0x28656). 무장 기록
  +0x18 통솔, +0x19 무력, +0x1A 지력, +0x21 레벨. r = 도달 코드, P(u) = INT + LV × INT / 100.
  `rand(n)`(0xcf5:0x48C4, 이미지 0x11814)은 `random % n`, 곧 `0 ≤ r < n`입니다 **[코드]**.
  * 공격(0–14): 기본 위력 `100 × (4r + e + 2)`(e = 화 0·수 1·낙석 2 = 번호 / 5), 피해 `기본 + 2 × (INT_c + LV_c × INT_c / 50)
    − (INT_t + LV_t × INT_t / 50)`, 군악대·주술사·수송대(병종 12·15·18) 대상은 절반, 숲(지형 1)의 화계와 비 오는 날의 수계는
    +25 %, 그 뒤 `rand(D / 50)`을 더하고 대상 병력으로 자릅니다(지형 방어·최소 1 없음). 명중은 `rand(P_c) > P_t / 4`
    (책략 방어 병종은 우변 2배). 大(3·4·8·9·13·14)는 십자(목표 칸 + 상하좌우)의 적마다 따로 굴리고, 원소가 맞지 않는
    칸은 건너뜁니다.
  * 혼란(15–17): 명중 `rand(P_c) > P_t / 2`. 위장(17)은 십자. 기간이 없고 `rand(100) < (통솔 + 사기) / 3`이면 풀립니다
    (0x24C90). 이 굴림은 적군 측(이미지 0x20AD1, 유닛 15–44, 지형 회복 0x1cb6:0x7CC8 바로 뒤)·아군 측(0x210F4, 유닛
    0–14) 페이즈를 시작할 때와, 사기 함수(0x1cb6:0x898C)가 사기를 **올리거나 100으로 둘 때**(0x2554B) 합니다. 사기
    함수는 사기가 **내려가서 30 미만**이면 `rand(5) < 3`으로 혼란시키고(0x25533), 혼란 비트(마스크 2)를 켜는 곳은 이것과
    책략 대상 처리 넷뿐이라 **페이즈 시작의 저사기 혼란은 없습니다** **[코드]**. 지형·장비 회복(0x1cb6:0x7CC8, 이미지
    0x24828: 사기 회복 `통솔 / 10 + rand(5) + 1`)도 사기 함수로 정하므로(0x2497A) 사기 100에서도 풀림 굴림을 하고, 아군 측
    회복은 턴 끝(0x1cb6:0x3DB2, 이미지 0x20912; 턴 루프 0x21791)에 합니다. 물리 공격에서 방어자가 전멸하지 않았을 때만
    사기를 정하고(0x2B820), 방어자가 병력 0이거나 **혼란이면 반격을 취소**합니다(0x2B872–0x2B886) **[코드]**.
  * 사기 저하(18–20): `(r + 2) × 10 + LV_c / 10 − LV_t / 10`만큼(현재 사기까지), 명중은 공격과 같습니다. 새 사기가 30 미만이면
    60 %로 혼란.
  * 지원(21–29, 단계 = r): 병력 `(단계 + 1) × 600 + LV_c × INT_c / 20 + rand(10 %)`, 사기 `(단계 + 3) × 10 + LV_c / 10 +
    rand(10 %)`(모자란 만큼까지). 21–23 사기, 24–26 병력, 27–29 둘 다. 시전자 자신도 대상이 됩니다(범위 펼치기에 중심 칸을
    넣는 모드로 부름). 저사기 반감 같은 규칙은 없습니다.
  * 大 지원(30–35, 단계 = (번호 − 30) % 3): 시전자 중심 range8/12/20(단계), 시전자 포함, 같은 편 전원에 위와 같은 회복.
    30–32 사기, 33–35 병력. 도달 표의 값은 쓰지 않습니다.
  * 대상 없음·지형 불일치·비 오는 날 화계·회복할 것 없음은 MP 없이 취소되고, 빗나가면 MP를 씁니다.
  * **회복 아이템**(아이템 명령 이미지 0x27A6F–0x27B4B): 아이템 번호 27–32와 52–54만 회복 함수(0x28420)를 시전자 0xFF로
    부릅니다. 52–54는 단계 = 번호 − 52, 병력과 사기 둘 다, 나머지는 단계 = 번호 % 3이고 30 미만(27–29)이면 사기, 그
    밖(30–32)은 병력입니다. 시전자가 0xFF면 보너스(`LV × INT / 20`, `LV / 10`)만 빠지고 `rand(10 %)`는 그대로라,
    병력 `(단계 + 1) × 600`, 사기 `(단계 + 3) × 10`에 10 % 안의 난수를 더합니다. 한국어판 이름은 27 술·28 특급주·29 빼갈,
    30 콩·31 보리·32 쌀, 52 상약·53 한방약·54 차입니다.
  * **변환**: 원작 모드의 `rules/strategies.toml`에 공격 위력, 사기 저하량, 지원의 병력·사기 기본값, 大 지원의 도달·범위를
    이 식대로 넣습니다(`pack::original_effect`). 기본 팩과 같은 값(공격·사기 저하)도 있습니다. 엔진과 식이 다른 부분(지원
    보너스·저사기 반감·난수, 혼란 명중 나눗수와 풀림, 사기 저하 혼란, 최소 피해 1, 피해 난수의 상한, 회복 아이템 난수)은 `rules/game.toml`의
    `strategy_formulas = "original"`로 고르고, 원작 모드 팩이 이 값을 씁니다(RULES §5). 책략 방어 병종의 반감과 숲에서만 붙는
    화계 보너스는 엔진·기본 팩과 같습니다(피해 계산의 순서만 다름). 원작의 명중 `rand(P_c) > P_t / 4`는 엔진의
    `100 − 100 × P_t / (4 × P_c)` %로 둡니다(같은 확률에 가까움).
* 맵 32번의 한 칸 (5, 13)에 코드 **255**가 있습니다. 게임에는 맵 밖과 같은 값이고, 지형 번호로 표를 읽는 코드는 이
  값을 따로 거르지 않아 표 뒤의 문자열 바이트를 읽습니다 **[코드]**. 한국어판에서 비용으로 읽히는 값은 이동 종류마다
  174 이상이라 **이동으로는 들어갈 수 없습니다**. 다만 비용이 `0xFF`인지만 보는 코드는 이 칸을 들어갈 수 있는 칸으로
  칩니다: 유닛 등장 때 빈 칸을 찾는 배치 탐색(이미지 0x2466C), `set_ai` 목표 칸 확인(0x26B39), 이동 예산 `0xFF`로
  부르는 AI 먼 거리 탐색(0x29A88 등). 정보창(0x23DD4)은 효과와 이름도 표 밖에서 읽습니다. 변환기는 이동 쪽을 따라
  이 칸을 절벽(9, 모든 이동 종류가 들어갈 수 없음)으로 옮깁니다(근사). 맵 32는 아직 변환하는 전투가 쓰지 않습니다.
* **칩별 지형 통계**: `maps/battle.json`의 `chip_terrain`은 칩마다, 그 칩이 그려진 칸의 지형 코드를 전 맵에서 센

### 10.6 캠페인 맵 `MMAP.R3` **[검증]**

```text
[W×H 타일][(W/2)×(H/2) 비트]
```

* 타일은 `MMAPBGPL` 0번(255셀) 번호.

### 10.7 도시 `SMAP.R3`(12) / 궁궐 `PMAP.R3`(23) **[검증: 배치] [미상: 물체]**

### 11.1 `SNR0M`–`SNR4M.R3` **[검증]**

압축되지 않은 파일(구현은 LS11 단일 항목도 받음).

```text
[u16 섹션 기준 × N][섹션 0][섹션 1]…      첫 기준 = 2N, 섹션 i = SNRnD의 장면 i
```

* **64 KiB 넘침**: 기준은 16비트인데 `SNR3M`(106,704바이트)은 64 KiB를 넘습니다. 3·4번 기준은 잘려 0x1029 / 0x59D0으로
  저장되고 실제는 0x11029 / 0x159D0입니다. 게임은 이 두 값을 코드에 박아 두고 0x10000을 더합니다 **[코드]**. 파서는
  "앞 기준보다 작으면 넘친 것"으로 일반화해 같은 결과를 냅니다(실제 기준은 순증가).
* **섹션 내용**(**정정**: NUL로 나뉜 문자열 목록이 아님): 항목 경계는 **바이트코드만** 압니다. 항목은 두 종류입니다.
  * **평문 문자열**: 서술·캡션·제목·선택지·전투 목표. EUC-KR + `00`. 앞에는 `00` 또는 대화의 `FF FF`가 옵니다.
  * **대화**: `[u16 화자][텍스트][00]`의 반복을 `u16 0xFFFF`가 끝냅니다. 화자 = `BAKDATA` 무장 번호(0–383). 게임은 대화
    하나를 1 KiB 버퍼로 읽습니다.
* 선택지 문자열은 줄바꿈(0x0A)으로 선택지를 나눕니다.
* 불변식: 18개 섹션의 **모든 바이트**가 스크립트가 가리키는 대화·문자열로 정확히 덮입니다(남는 바이트 0). 한국어판:
  서로 다른 대화 2,619개(4,783줄), 평문 문자열 901개, `SNR0M` 10,920바이트. 모두 EUC-KR로 깨끗하게 디코딩됩니다.
  (다른 프로젝트가 공개한 "블록 5,677개"는 세는 방식이 문서화되지 않아 쓰지 않습니다.)
* 메시지 표의 섹션 수(첫 값 / 2)는 `SNRnD`의 장면 수와 같아야 합니다(1/5/4/5/3).

코드: `ippan.rs` **[검증]**.

* `IPPAN0.R3`(압축 없음, 3,640바이트)는 제1–4장용 조각 4개(957 / 785 / 1,047 / 851바이트)가 이어 붙은 것입니다(서장
  없음). 조각 경계는 `MAIN.EXE`의 오프셋·길이 표와 같고, 조각 자체로도 끝을 알 수 있습니다.

  ```text
  [u8 n][n × u16 마을 레코드 오프셋 (조각의 1번째 바이트 기준, 0 = 없음)]
  [u16 m][m × u16 문자열 오프셋 (이 장의 IPPAN0M 구간 기준, FFFF = 없음)]
  마을 레코드: [u8 g] g × ([u8 키][u8 k][k × u16 항목])
  ```

* 장 c의 `IPPAN0M` 구간은 장 c−1이 참조한 마지막 문자열 끝에서 시작합니다(0, 11,301, 20,619, 31,291 — `MAIN.EXE`의
  표와 같음). 네 장이 653개 문자열을 빠짐없이 한 번씩 가리킵니다.
* 스크립트 명령 `0x1F`가 이 표를 씁니다: 현재 마을의 그룹 중 키가 게임 상태 값과 맞는 것(**키 125 = 기본 그룹**)을
  골라, 항목마다 32×20 맵의 빈 칸에 무작위로 세웁니다 **[코드]**.
* **항목 번호 = `BAKDATA` 마을 사람 번호(이름·스프라이트) = 그 사람이 하는 대사 번호**입니다(대사 내용과 직업이
  맞는지로 확인).
* **[미상]**: 키가 125가 아닐 때 비교하는 상태 값, 마을 번호와 맵 번호의 대응.

## 13. 시나리오 바이트코드 `SNRnD`

코드: `scenario.rs`. 배치는 실물 데이터를 끝까지 걸어 보며(모든 바이트가 설명되는지) 확인했고, 명령 집합은
`MAIN.EXE`의 스크립트 인터프리터(명령 분기, 처리기별 피연산자 읽기, 처리기가 찍는 디버그 문자열)를 정적으로 읽어
정했습니다.

### 13.1 구조 **[검증]**

```text
SNRnD.R3   LS11 아카이브, 항목 = 장면 (n = 0..4에 대해 1/5/4/5/3개, 합 18)
장면       [u16 블록 오프셋]… FFFF
블록       [10바이트 트리거 레코드]… [FF × 10]   그 뒤 스크립트들
레코드     [종류][그룹][u16 a][u16 b][u16 c][u16 스크립트 오프셋 (블록 시작 기준)]
스크립트   [명령][피연산자]… FF
```

* 한국어판: 블록 225개, 레코드 2,144개, 명령 14,404개. 18개 장면의 모든 바이트가 블록 표·레코드·스크립트로 덮입니다.
  서장의 블록 오프셋 표(10개)는 골든 테스트의 확인값입니다.
* **정정**: 노트의 "이벤트 오프셋 표"는 블록 표이고, 10바이트 레코드는 유닛 슬롯이 아니라 트리거입니다(유닛 배치는
  명령 `0x03`/`0x22` 안에 있음).
* 메시지 피연산자 = 그 장면 섹션(`SNRnM`) 안의 바이트 오프셋, 인물 피연산자 = `BAKDATA` 무장 번호.

### 13.2 트리거 레코드

* **종류 바이트**: 하위 7비트 = 종류, 비트 7 = 판정 반전(정확한 의미 **[미상]**).
* **그룹 바이트**: 하위 7비트 = 그룹, 비트 7 = 그룹 플래그(그룹 첫 레코드의 것). 전투 블록에서는 병행 제어 그룹의
  표시입니다(아래). 다른 블록에서의 역할은 **[미상]**.
* 같은 그룹의 연속 레코드는 한 사건의 후보입니다. 게임은 차례로 판정해 **처음 성립하는 것**의 스크립트를 실행하고,
  끝나면 다음 그룹으로 넘어갑니다 **[코드]**.
* **전투 블록의 그룹 = 단계** **[검증: 서장·1장 21개 전투]**: 그룹 0은 명단과 `load_map`(4장 장면 2의 마지막 두 전투는 앞 전투가 끝난 자리에서 출진 설정 뒤 `battle_end next_map=0x30NN`으로 맵을 불러옴, 이슈 #95), 1은 `begin_battle`, 2는 개막
  (대사·초기 `set_ai`·조운 같은 개막 합류), 3부터가 전투 중 단계입니다. 첫 레코드에 그룹 플래그가 있는 그룹은 **병행
  제어**로, 그룹의 모든 레코드(일기토·턴·보물·영역·승리)를 함께 지켜보다가 어느 스크립트가 `leave_parallel`(`0x13`)을
  실행하면 다음 그룹으로 넘어갑니다. 플래그가 없는 그룹은 위 규칙대로 처음 성립하는 레코드 하나를 실행하고 넘어갑니다
  (서주 2: 차주 격파 → 서주 입성 영역 → 목표 칸). `run` 레코드만 있는 그룹은 단계 사이나 전투 뒤의 스크립트이고,
  `battle_end`(`0x11`)가 있으면 전투가 끝난 뒤(승리)입니다. 레코드는 여러 번 성립할 수 있어서, 한 번만 실행할 것(보물 칸
  등)은 스크립트 첫 `if_flags`와 `set_flag`로 막습니다. 하비의 적교 칸처럼 다른 레코드가 켠 플래그를 요구하는 레코드도
  있습니다(후성·위속·송겸 일기토가 플래그 17·18·19를 켬).
* 선택지(`0x25`)의 i번째 답은 "현재 레코드 + 1 + i"의 스크립트로 갑니다 **[코드]**.

  30 × 9바이트 `[u16 무장][x][y][0이면 적 편][조건 여부][플래그][?][?]`. 빈 슬롯은 무장 = FFFF.
* **`0x22` battle_roster (0x187 = 391바이트)**: `[방식: 0 = 적, 그 외 = 우군 NPC]` + 30 × 13바이트
  `[u16 무장][x][y][조건 여부][플래그][?][?][AI 방식][u16 AI 인자][병종][레벨]`.
* 확인: 서장 사수관 30턴·화웅 격파 승리, 호로관 여포, 조건부 우군(공손찬·도겸 — 말을 걸면 켜지는 플래그 0·1을 요구),
  적장 병종·레벨(화웅 경기병 Lv5, 여포 Lv6)이 공개 공략과 일치합니다.
* **좌표축 [검증]**: 두 좌표 바이트 중 첫째가 **열(x)**. 서장·1장 19개 전투의 모든 명단·슬롯 칸이 이 순서로만 맵 안에
  들어간다(예: 호로관 16×24의 유비 (15, 21)). 트리거 레코드의 칸은 반대로 **행이 먼저**(13.2).
* **슬롯의 남은 바이트 [검증]**: `0x03` 아군 슬롯의 셋째 미상 바이트 = 1이면 그 무장은 처음에 맵에 없고, 전투 블록의
  `join_battle`(`0x1A`)이 데려온다(서주 1 태사자 5턴, 하비 조조군 30턴 또는 (12, 12) 칸, 계교 조운은 전투 시작 직후의
  `run` 레코드). `0x22` 명단 칸의 둘째 미상 바이트 = 1도 같은 뜻(서주 2 조조군 19부대, 회남 진궁·장요 등 10부대).
  무장 `0x400`인 아군 슬롯 = 아무 출전 무장. 코드로는 출전 슬롯의 마지막 바이트 ≥ 1, 명단 칸의 둘째 미상 바이트 ≠ 0이면
  배치 기록의 비트1("나중에 합류")이 켜진다 **[코드]**(아래).
* **참전 위치 (`join_battle`) [코드]**: 처리기(명령 분기 이미지 0x157E4의 `dec ax` 사슬에서 0x15ED2)는 무장 번호만 읽고,
  공용 배치 루틴 0x168D4 → 참전 함수 0x2CBBE로 간다(칸 인자는 쓰지 않음). 그 무장의 유닛이 맵에 없음(유닛 표 DS 0xE2A2,
  45개 × 14바이트, +0 무장, +3/+4 x·y, +9 상태 = 1)일 때만 움직이며, 배치 기록 표 DS 0xD6A9(45개 × 11바이트
  `[u16 무장][x][y][비트]` + AI 정보; `battle_setup`이 비우고 채우고 `battle_roster`가 덧붙임, 비트0 적 편, 비트1 나중에 합류)를
  0번부터 훑어 그 무장의 첫 기록의 칸에 놓는다(0x24F82). 그 칸에 유닛이 있거나 병종이 못 가는 지형(이동 종류 DS 0x3FFA,
  비용 DS 0x400E, 0xFF = 통과 불가)이면 위·오른쪽·아래·왼쪽 순서(DS 0x4D1C)로 깊이 5까지 재귀 깊이 우선 탐색한다(0x24668,
  방문 표시 없음: 가장 가까운 칸이 아닐 수 있음). 전투 시작 배치도 같은 루틴이고, 비트1 기록은 그때 놓지 않고 상태 1로 둔다.
  출진 설정에 없는 무장의 `join_battle`은 아무 일도 하지 않는다(허창 1을 블록 5의 설정으로 치를 때: 별동대 넷의
  `join_battle`은 그 루트에서 플래그 89가 꺼져 `if_flags`가 건너뛰고, 플래그 94만 보는 강유의 것이 아무 일도 하지 않는다).
  칸이 맵 밖이면 놓지 않고, 깊이 5 안에 빈 칸이 없으면 x = 0xFF가 기록되는 것으로 보인다 **[추론]**.
* **AI 방식 (`0x1C`, 명단 AI 바이트)** **[코드]**: `set_ai` 처리기(이미지 0x15F46)가 부르는 설정 함수(0x2CE5A)가
  방식을 바이트 표 DS 0x4FE6(`u16` 간격)으로 내부 AI 코드로 바꿔 유닛의 +0x0B에 넣는다: 방식 0→3, 1→1, 2→2, 3·4→0,
  5·6→4. 내부 코드의 이름은 유닛 정보가 쓰는 문자열 표(DS 0x40A8, 먼 포인터 8개)에 있다: **0 이동, 1 최단 적공격,
  2 부동, 3 대기, 4 무공격이동**, 5 혼란, 6 마비, 7 입력(플레이어). AI 분기(이미지 0x29AD9)에서 이동(0)과
  무공격이동(4)은 목표 무장(`[유닛+5]`) 또는 목표 칸(`[유닛+6]`)으로 향하는 같은 경로, 최단 적공격(1)은 가장 가까운
  적을 치는 루틴(0x1cb6:0xDC00), 부동(2)은 이동 0으로 공격 대상을 찾고(제자리에서만 공격), 대기(3)는 이동+공격
  범위 안에 적이 있으면 가서 치고 없으면 제자리에 있다. 그래서 방식 0 = 대기, 1 = 최단 적공격, 2 = 부동, 3 = 목표
  무장으로 이동, 4 = 목표 칸으로 이동, 5 = 목표 무장으로 무공격이동, 6 = 목표 칸으로 무공격이동이다. 호로관 여포가
  명단 2(부동)에서 18턴 `set_ai` 1로 바뀌고 공략에서도 18턴에 관문을 나선다 **[검증]**. 칸 인자는 **하위 바이트 =
  열**(30×18 서주 명단은 반대로 읽으면 맵 밖) **[검증: 칸]**.
* **분기 명단**: 전투 블록이 `if_flags`로 명단 하나를 고르는 경우가 있다. 계교는 플래그 133(거록 경로를 고르면 켜짐,
  `SNR1D` 장면 0 블록 10) 여부로 19부대/17부대 명단을 고른다 **[검증]**.

### 13.5 맵 칸 변경 (`0x26`) **[코드] [검증]**

`MAIN.EXE`의 처리기(한국어판 이미지 0x163CD, 디버그 문자열 "マップチップ変更")가 부르는 함수(이미지 0x2D126)를 읽어
정했습니다. 좌표는 칸(32 px, 2×2 칩)이고 첫 값이 열입니다. 동작 값의 비트 7은 다시 그리기 기록용이고 하위 7비트가
동작입니다. 표 네 개는 코드 서명으로 찾습니다(15.2).

| 동작 | 이름 | 조건 | 칩 | 지형 |
|---|---|---|---|---|
| 0 | 성문 열기 | 칸의 지형 = 표[0] (10, 문) | 칩마다 + 변화량[세트][0] (첫 세트 +8, 둘째 세트 +17), 단 0xC5 → 0xC7, 0xC6 → 0xE6 | 표[1] (0, 평지) |
| 1 | 성문 닫기 | 지형 = 표[1] | 변화량[세트][1] (−8 / −17), 고정 치환은 동작 0과 같음 | 표[0] |
| 2 | 적교 내리기 | 없음 | 칩마다 치환 표 9쌍(0xD9 → 0xD2 … 0xDA → 0xD3)을 차례로 적용 | 새 칩에 0xD3이 있으면 표[3] (4, 다리), 없으면 그대로 |
| 3 | (적교 올리기) | 지형 = 표[3] | 변화량[세트][3], 고정 치환은 동작 0과 같음 — 둘째 세트의 값은 쓰레기 값 | 표[2] (3, 개울) |

* 0xC5·0xC6의 고정 치환은 적교(2)가 아닌 모든 동작의 칩 루프에 있습니다. 그래서 열고 닫기를 반복해도 칩이 처음으로
  돌아온다는 보장은 없습니다(게임의 동작 그대로).
* "세트"는 맵이 `HEXZCHP` 2번을 쓰는지(10.2의 맵 목록)입니다. 한국어판 표: 지형 쌍 DS 0x4FF6 = `[10, 0, 3, 4]`,
  변화량 DS 0x4FFA(`i16` 2 × 4), 치환 DS 0x500C → 0x5015.
* 데이터에서 쓰는 값은 0(북해 성문, 2회)·1(1회)·2(하비 적교, 18회)뿐입니다. 하비 적교는 여섯 칸 중 가운데 칸
  (12, 11)만 다리가 되고 나머지는 칩만 바뀝니다. 바꾼 칩으로 그린 그림이 원작 맵의 열린 성문·내린 적교와 맞습니다
  (컨택트 시트로 확인).

### 13.6 일기토 연출 (`0x10`·`0x34`·`0x35`·`0x33`) **[코드]**

코드: `battles.rs`(`duel_moves`), `pack.rs`(`duel_pictures`). 한국어판 이미지 오프셋(헤더 0x6A00 제외).

* `0x10 duel(first, second)`(0x15D22)이 장면을 엽니다(0x2DD9E): 두 무장이 26칸 폭(16 px 칸, 전투 틀의 맵 구멍 416 px)의
  무대에서 x = 7(first, 왼쪽)과 13(second, 오른쪽), y = 3칸에 섭니다. 배경은 무장이 선 칸의 지형 코드로 DS 0x4E42(하늘 띠)·
  0x4E56(땅 띠) 표를 찾아 `HEXBMAP` 띠(§10.5)를 그립니다.
* 기마 그림 `HEXICHR`: 세트 5개 × 15프레임(0–3 질주, 4–11 공격 두 장씩, 12 낙마, 13·14 말 옆에 쓰러짐(두 자세)) + 궁기병 3장. 모든
  세트가 오른쪽을 봅니다. 세트는 인물 번호 < 5이면 DS 0x5048 표(`ff 02 03 ff 04`: 1 → 2, 2 → 3, 4 → 4), 372 → 2,
  373 → 3, 그 밖은 자리(0 왼쪽, 1 오른쪽)입니다(0x2D91C).
* `0x35 duel_action(person, action)`(0x2E010): 0·1·2 = 공격 프레임 4·6·8부터 두 장(0·1은 먼저 상대 네 칸 앞까지 질주),
  3 = 낙마(프레임 12·13), 4 = 도주(14걸음 질주로 무대 밖), 5 = 대기, 6·7 = 질주 + 공격 4·6(0·1과 효과음만 다름),
  8 = 효과(0x115e(10)), 9 = 처음 자리로 돌아감, 10 = 질주. 효과음 번호는 DS 0x5082(40, 41, 23, –, –, 13, 38, 39).
* **변환** **[추론: 배경·8번]**: 원작 모드 팩은 `@duel`·`@duel_act`·`@duel_end`로 옮기고, 세트 0·1을 `gfx/duel/left`·`right`,
  제 세트가 있는 인물을 그 무장 id로, 지형 코드마다 하늘·땅 띠의 왼쪽 416 px를 그 지형의 팩 지형 id로
  `gfx/duel/terrain_<id>`에 씁니다. 이벤트 때의 위치는 변환할 때 알 수 없으므로 `@duel … terrain`으로 두고, 게임이 전투
  중 왼쪽(first) 무장이 선 칸의 지형으로 고릅니다(그 무장이 맵에 없으면 오른쪽 무장; 원작이 두 무장 중 누구의 칸을 보는지는
  [추론]). 8번은 공격 10으로 옮깁니다.
  효과음·타이밍(0x2502·0x5C38)은 따라가지 않고 엔진의 걸음·타격·퇴각 소리를 씁니다.

코드: `bakdata.rs`. 19,328바이트, **압축 없음** **[검증]**. `MAIN.EXE`의 로더가 정확히 네 구간(0xD00, 0x400, 0x1F80,

|---|---|---|

  맹수군단, 무술가, 요술사, 이민족, 민중, 운송대(이름 목록은 `MAIN.EXE`에 있음).
* **아이템 종류** **[추론: 그 종류의 아이템들로 명명]**: 0 무기(위력 = 공격 % 보정), 1 전직 도구, 2 공격 책략서·폭탄,
  3 소모품·특수, 4 말(위력 = 이동력), 5 병법서(위력 = 방어 % 보정). 초기 소지 확인 예: 관우 = 청룡언월도, 장비 = 사모,
  여포 = 적토마·방천화극.
* **[미상]**: 역할 바이트(유비만 0, 로더는 값 + 2로 보관), 무장 플래그 바이트(20번째), 무장·마을 사람 스프라이트 번호가

* 초기 상태 18바이트 레코드는 공개된 `MSAVE` 무장 레코드(18바이트, 같은 필드 순서)와 모양이 같습니다 **[추론]**(16절).

## 15. `MAIN.EXE`: 데이터 세그먼트와 코드 서명

`MAIN.EXE`는 표의 보고입니다. 구현은 **표를 저장소에 복사하지 않고, 사용자의 실행 파일에서 그 표를 읽는 코드를 찾아**
주소를 얻습니다(`maps::find_exe_tables`, `palette::find_bank`). 같은 방법은 다른 빌드에도 그대로 적용됩니다.

### 15.1 데이터 세그먼트 **[검증]**

* 한국어판: MZ 헤더 0x6A00바이트(재배치 6,776개), DGROUP = 0x313A → 데이터 세그먼트 파일 위치 0x37DA0.
* **DGROUP 찾기**: MZ 헤더에서 헤더 크기(0x08, 문단 단위), 진입점 IP(0x14)·CS(0x16)를 읽어 진입점 파일 위치
  `헤더 × 16 + CS × 16 + IP`로 갑니다. C 런타임 시작 코드가 DOS 버전 검사 뒤 `mov di, DGROUP`을 합니다:

  ```text
  B4 30 CD 21 3C 02 73 05 33 C0 06 50 CB BF <DGROUP u16>
  mov ah,30h / int 21h / cmp al,2 / jae +5 / xor ax,ax / push es / push ax / retf / mov di,DGROUP
  ```

* 데이터 세그먼트 파일 위치 = 헤더 크기 × 16 + DGROUP × 16.

## 16. 음악 **[코드] [검증]**·세이브·글꼴 (미검증)

코드: `music.rs`, `opl.rs`.

* **파일** `MUSIC.R3`(20곡), `OPMUSIC.R3`(2), `EDMUSIC.R3`(3): LS11이 아님. `[u16le 개수][개수 × (u32le 오프셋, u16le 길이)]`,
  곡 위치 = 2 + 개수 × 6 + 오프셋 **[검증]**. 곡 = 트랙 오프셋 `u16` 7개(0 = 없는 트랙; 재생기는 8번째 워드도 읽어 채널 7 = 효과음 자리에 두지만 음악 스텝은 채널 0–6만 진행), 그 뒤 22바이트 악기 8개, 트랙
  스트림 **[검증]**: 25곡 모두 트랙마다 이벤트를 끝까지 읽은 총 스텝 수가 같습니다(예: `MUSIC` 0번 5376스텝).
* **재생기** `SBOPL2.COM`(KOEI "Sound Blaster BGM Driver 1.01") **[코드]**: 채널 0–6이 음악, 7–8은 효과음. 채널 기록 0x30바이트
  (COM 0x56A부터), 채널 번호와 연산자 오프셋(0,1,2,8,9,A,10)은 고정. 초기화 레지스터 01=20(파형 선택), 08=40(NTS), BD=00.
* **시계** **[코드]**: PC 타이머를 1193182/4096 Hz로 돌리고(원래 인터럽트는 16번에 한 번), 틱마다 16비트 누산기에
  `템포 × 0x464E / 100`을 더해 넘칠 때 한 스텝(템포 120 ≈ 96 스텝/초), 8비트 누산기에 0x36을 더해 넘칠 때 효과 프레임
  (≈ 61 Hz)을 진행합니다.
* **이벤트** **[코드]**(처리기 표 COM 0xCA3):
  * `00`–`5F` 음 + 길이 바이트 + 게이트 바이트(게이트 0 = 쉼표, 게이트 > 길이 = 다음 같은 음으로 이어짐), `60`–`BF` 음 − 0x60
    (앞 길이·게이트). 음 + 악기 이조 = 12로 나눠 블록·반음, F-번호 표 12개(COM 0x76A).
  * `D0` 반복 시작, `Dn` 앞 구간 n+1번, `FD` 마지막 회차에 반복 탈출, `FE` 루프 지점, `FF` 끝(루프 켜짐이면 루프 지점으로).
  * `F0 v` 볼륨(감쇠, 연결 비트가 켜진 연산자의 TL에 v/2), `F1 b`·`F2 t` 템포, `F4 rel16` 악기(이벤트 위치 + rel), `F6`/`F7`
    음높이 슬라이드(반음 수 부호·시간), `F8`/`F9` 악기 LFO 켬/끔, `EE`/`EF` BD 비트 7·6, `C0`–`CF`·`FA`–`FC` 무시,
    `E0`–`ED`·`F3` 1바이트·`F5` 2바이트 건너뜀.
* **악기 22바이트** **[코드]**: 0–10 = 레지스터 20+op, 23+op, C0+ch, E0+op, E3+op, 40+op, 43+op, 60+op, 63+op, 80+op, 83+op 값,
  11 = 이조(부호), 12–13 = LFO 속도, 14 = LFO 파형(0 톱니, 1 사각, 2 삼각, 3 무작위, 4 한 번 오르기), 15 = 음높이 깊이(부호),
  16 = 깊이 배율 표 번호(COM 0x74A), 17 = 음량 깊이(부호), 18–19 = 연산자별 음량 깊이, 20 = 지연, 21 = LFO 있음.
* **변환** **[추론: 곡 배정]**: 원작 모드 팩은 곡을 재생기와 같게 연주해 자체 OPL2 에뮬레이터(3.579545 MHz / 72,
  로그 사인·지수 표, 칩의 엔벨로프 속도 표)로 22050 Hz 16비트 모노 `bgm/<키>.wav`를 씁니다(칩 샘플 약 49716 Hz를
  블랙먼 창 sinc 저역 통과 필터 128탭으로 줄여, 11025 Hz 위의 FM 배음이 가청 대역으로 접혀 들어오지 않게 합니다). 재생기는 `FF`에서 트랙마다
  `FE` 지점(없으면 트랙 시작)으로 돌아갑니다. 곡 전체는 마지막 트랙의 루프 지점부터, 트랙 루프 길이들의 최소공배수마다
  되풀이됩니다. 변환은 그 한 바퀴를 **두 번째 바퀴에서** 떠 박자상 이음새 없이 반복되게 합니다(바퀴마다 누산기·LFO 상태가 달라
  길이가 최대 1 타이머 틱, 약 3.4 ms 다를 수 있는 근사). 그 앞의 인트로(battle 2.7초, defeat 0.8초, sad 0.4초)는 같은 파일 앞에
  두고, WAV `smpl` 청크에 루프 시작 프레임을 적습니다. 게임은 인트로를 한 번 틀고 루프를 반복합니다(ROADMAP M5-5).
  인트로의 끝 음이 남기는 잔향은 루프가 시작되는 곳에서 끊기고, 대신 루프 끝의 잔향이 들립니다. 엔진도 프레임 경계에서 파일을
  바꾸므로 피할 수 없는 근사입니다. 트랙마다 루프 지점이 다른 곡(`EDMUSIC` 0번: 트랙 2·5에 `FE`가 없음)도 같은 규칙을 따릅니다.
  다만 최소공배수 주기가 600초를 넘으면 처음부터 한 번 연주하고 이음새가 남습니다. `EDMUSIC` 0번이 어느 쪽인지는 아직 확인하지
  않았습니다. 어느 곡이 어느 키인지는
  시나리오의 `0x38` 문맥으로 골랐습니다(ORIGINAL_DATA). 게임이 전투 중에 트는 곡은 MAIN.EXE가 `int 65h` 쪽 경로로 고르며
  아직 따라가지 못했습니다.
* **세이브** `E*.R3S`(진행 상태)·`M*.R3S`(무장 상태), 슬롯 5개씩. `MSAVE`의 무장 레코드는 18바이트
  `[소속][역할][00 00][사기로 보이는 값][u16 병력][병종][레벨][경험치][아이템 × 8]`로 공개되어 있고, 이는 `BAKDATA` 초기 상태
  레코드(14절)와 같은 모양입니다 **[추론]**. 나머지 형식은 모릅니다.
* **글꼴** `ALL_FONT.16P`(KS X 1001 16 px 한글 비트맵, 32바이트 간격: 2바이트 코드 + 30바이트 비트맵), `FONT.R3`,
  `HANKAKU.FNT`. 우리 게임은 자체 글꼴을 쓰므로 필요하지 않습니다.
